## 第 0 节 · 三条铁律（违反即出事，最高优先）

1. **无银发信号的企业/资讯直接删**，绝不进"行业服务"兜底桶。判定以业务实质为准，关键词只是辅助，不确定就联网核查、默认从严。
2. **只认一个门禁**：`scores_draft/rework/check_single.py`（recommend）+ `check_description.py`（description）。不自造平行规则、不另开门禁。
3. **改真相源必增量、必备份**：合并进 `all_enterprises.json` 只更新候选字段、不覆盖其他记录；任何二次合并走增量，禁止全量重跑覆盖已部署好稿。

> 行为准则（不擅自入库/部署、改小爽手标必标注、有独立判断等）见同目录《企业库行为准则.md》，本手册不重复。

## 第 1 节 · 基本盘（我是谁 / 数据在哪 / 归我管什么）

**关键位置**：

**我的职责**：企业库的**数据 + 前端渲染 + 部署 + 文档与记忆**全部归我，所有在用字段我都要维护（只读/废弃字段除外，见 §6.1）。**标签只在既有二级标签体系内选 1~3 写入 `tag_l2`，不自造新词**（新词由标签 AI 定义）。

**小爽**：定方向、做最终审核与发布放行。

## 第 2 节 · 主流程（一张图看懂：先干什么、后干什么）

### 2.1 先定位：我这次的任务从哪一步进？

所有任务走**同一条 10 步主流程**，只是入口和终点不同：

| 我这次要做的 | 从第几步进 | 说明 |
|---|---|---|
| 小爽给企业名单 / 月度扫描发现新企业 / 外部 AI 交来名单 | **步骤 1 起，完整走到 10** | 最常见。外部 AI 名单先放 `handoff/enterprise_inbox/`，再从步骤 1 走（详见 §4.1） |
| 存量走查发现问题（英文待译、模板话术、漏打标等） | **步骤 3 起** | 准入（1）、去重（2）此前已做过，跳过 |
| 纯 UI/UX 小改（文案、样式、布局微调） | **步骤 6 → 9，事后补审** | 轻量分支，不走步骤 8 硬审核（详见 §3.9 分支策略） |

### 2.2 十步主流程

| 步骤 | 做什么 | 谁做 | 用什么工具 | 产出 |
|---|---|---|---|---|
| **1 准入** | 银发相关性判断（无信号即删） | 脚本初筛 + AI 二筛 | 强词表 `config.SILVER_STRONG_KEYWORDS` | 通过 / 删 |
| **2 去重** | 对全库比对，判断新/已存在/疑似 | 脚本粗筛 + AI 裁决 | `dedup_keyword_prescreen.py` | 去重结果 |
| **3 补字段** | 联网/翻译补齐所有在用字段 | AI 为主 | 联网 + 翻译；顺手记引用网址 | 全字段齐 |
| **4 推荐理由** | 写 recommend | AI 强模 | — | recommend |
| **5 评分** | 信号强度 + 四维精评 | 脚本 + AI | `signal_strength.py` + `merge_batch_scores.py` | 四维分 + total |
| **6 前端校验** | 生成卡片、肉眼看渲染 | 脚本 + 人眼 | `gen_enterprise.py` | 卡片预览 |
| **7 质量校验** | 门禁自测 + 语义走查 | 脚本门禁 + AI 走查 | `check_single.py`+`check_description.py`+ 子智能体 | 问题清单 |
| **8 小爽审核** | 发预览表 + 审核附言 | **人工卡点** | 全字段 Excel + 附言 | 放行 / 驳回 |
| **9 合并部署** | 编辑真相源→生成→部署 | 脚本一条命令 | `enterprise_build.py` | 上线 |
| **10 上线走查** | 抽查渲染/排序，问题回滚 | AI + 人眼 | 子智能体 | 验收 / 回滚 |

> **贯穿全程的"工作产物"= 候选文件**：新企业在入库过程中不是直接写真相源，而是先存成**候选 JSON**（放 `scores_draft/rework/drafts_v5/` 目录，或单独一个 `候选.json`）。步骤 1–8 全部在这个候选文件上操作（准入判断、去重结果、补的字段、recommend、评分都写进它），步骤 9 才用它**增量合并**进真相源 `all_enterprises.json`。
> **格式**：与真相源记录同构的字段字典数组（`[{"serial":"#XXXX","name":...,"description":...,...}, ...]`），字段定义见 §6.1。这就是各脚本 `--candidates 候选.json` 参数要的文件。

> **节点分两类**：**纯脚本节点**（1初筛/2粗筛/5/6/7门禁/9）确定性计算，能串就串成一条命令；**AI 必须介入的节点**（1二筛/2裁决/3/4/7走查/10）需要语义判断。**AI 只在必须介入的节点动脑，中间数据传递交脚本**——这是省积分的核心。步骤 8 永远是人工，不自动化。

### 2.3 卡住了怎么办

- **脚本报错** → 看报错信息修数据格式，重跑。
- **AI 判断拿不准** → 标"待小爽定"，带进步骤 8 让小爽拍板，**不阻塞其他企业**。
- **单家不阻塞批量** → 一批 20 家里 3 家有争议，先把 17 家推下一步，3 家标"待定"单独处理。
- **小爽驳回** → 只修有问题的部分，见 §3.7 驳回流程。

## 第 3 节 · 每步详细规则（与步骤编号一一对应）

### 3.1 步骤 1 · 银发相关性准入（两阶段）

**阶段一 · 强词初筛（脚本）**：`config.SILVER_STRONG_KEYWORDS`（约 67 个中英文强词），被 `selection/relevance_screener.py` 使用。命中→进二筛；未命中→原则上拒（除非有特殊理由）。

```python
from config import SILVER_STRONG_KEYWORDS
text = (name or "") + " " + (description or "")
hit = any(kw in text for kw in SILVER_STRONG_KEYWORDS)
```

强词清单（约 67 个）：养老/老年/老人/银发/长者/长辈/退休/适老/适老化/照护/康养/医养/助老/陪护/康护/颐养/老年病/长寿/居家护理/居家照护/康复/慢病/认知症/痴呆/阿尔茨海默/失智/失能/护理院/养老院/敬老院/养老社区/养老产业/银发经济/养老金融/养老科技；英文 aging/elderly/senior/senior care/elder care/aged care/dementia/alzheimer/long-term care/nursing home/assisted living/home care/caregiver/caregiving/hospice/medicare/medicaid/retirement/senior living/pace program/value-based care/older adult/silver economy/age tech/memory care/senior housing。

**阶段二 · AI 二筛（低模是非题）**，符合任一即保留：
- 直接面向 **50/60 岁+人群**（C 端）；
- 面向 **Medicare/Medicare Advantage 参保老人**（C 端）；
- 为上述"服务 C 端老人的 B 端企业"提供产品/服务。

**直接拒绝**（不论是否命中强词）：综合电商（养老仅"规划中"）、品牌 PR/活动传播、Web3/通用 AI 平台、泛再生医学/高端医疗绿通、泛医疗 VC、泛融媒体。

> 关键词是辅助，**最终以业务实质判断为准**，不确定联网核查、默认从严。

### 3.2 步骤 2 · 全库去重

**比对对象必须是全库 `all_enterprises.json`。**

**先跑脚本粗筛**：`python scores_draft/rework/dedup_keyword_prescreen.py --name "企业名"`（或 `--candidates 候选.json`）。
原理：提取核心名（去括注→去公司后缀→去城市国家前缀，循环到稳定）→ 用核心词在全库 name/name_cn 双向子串匹配 → 输出"疑似重复候选"清单。

> **粗筛只是"把名字相近的挑出来给 AI 看"，命中≠重复，最终由 AI 判定。**
> - 例：核心词"乐龄"命中"乐龄圈""康乐龄"——这是 **3 家不同企业**，AI 精比对后判不重复。
> - 分公司算一家：福寿康 / 上海福寿康xx / 昆明福寿康xx → **同一家的分支机构，合并为一家**，由 AI 模糊相似度校验负责认出。

**AI 精比对三情形**：

| 情形 | 处理 |
|---|---|
| **一致**（信息无差异） | 跳过，不新建 |
| **增量**（相似但有信息补充，含分公司） | 合并进已有记录，补增量字段；拿不准标"待小爽定" |
| **冲突**（疑似同家但关键业务矛盾） | 联网复核以证据订正，交小爽裁决 |

### 3.3 步骤 3 · 补全所有字段

联网/翻译补齐字段字典（§6.1）里所有在用字段。**补不到标"待补充"，禁止编造。**

- **必填最低门槛**：`serial`（格式 `#XXXX`，取最大值+1）/ `name` / `region` / `description(≥20字)` / `source` / `ingest_time` / `update_time`。
- **description（核心）**：中文、≥20 字，说清三件事——**做什么、服务谁、怎么赚钱**（信息不足至少前两件）；禁模板套话、禁英文主导、禁夹带原始标记（如【提供资源】）；金额用中文（万/亿）。
- **标签 `tag_l2`**：从 `data/enterprise/_l2_l1.json` 现有体系选 1~3；打标时顺手校验是否在词表内，不在即报警（别等走查才发现）；没有合适的向小爽提建议。
- **商业字段**（`funding_*`/investors/payor_model 等）：很重要但不一定有，能补则补。
- **搜索索引**（前端）= `name`(含 name_cn) + `description` + `tags`(tag_l1/tag_l2/同类词) + `stage` + `recommend`。

**引用网址记录与渠道去重（纯代码，不耗积分）**：补字段时把参考网址正常写进 `source_urls`/`reference_urls`/`website_url`/`crunchbase_url`。月度入库后跑一次 `python scripts/collect_source_urls.py`：
1. 按主域名（eTLD+1，忽略子域名/栏目）跨企业统计高频引用站点；
2. **与 `config.SOURCES` 现有渠道按主域名去重**（已在渠道库的不报备，只报个数）；
3. 输出"不在渠道库、被多家引用"的候选清单，走 §4.2 跨 AI 笔记交给信源 AI。

### 3.4 步骤 4 + 5 · 推荐理由与评分

**信号强度**（脚本 `selection/signal_strength.py`，`compute_signal_strength()`，0~10 封顶、保底 0.5，企业与资讯共用）：
- 信源起点：T1=0.5 / T2=0.3 / T3=0.1
- IPO=+6；融资(美元)：≥10亿=5/1亿=4/5000万=3/1000万=2/500万=1/100万=0.5
- 融资(人民币)：≥10亿=6/1亿=5/5000万=4/1000万=3/500万=2/100万=1/50万=0.5
- 收购：≥100亿=6/50亿=5/10亿=4/1亿=3/5000万=2/1000万=1
- 时效：近1周=2.5/近1月=2/近2月=1.5/近半年=1/近1年=0.5/更久=0.25

**四维评分公式**（`merge_batch_scores.py:66-72`）：
```
total_score = 信号强度×30% + 信息量×30% + 差异化×20% + 可复制×20%
```
- 每维 **0~10 分**、total **0~10 分**（均防御性封顶）；内部全程 0~10 分制；**前端展示 ×10 → 0~100**（`gen_enterprise.py:357`）。

**怎么跑（顺序）**：① 先跑 `selection/signal_strength.py` 回填每家 `signal_strength`；② 四维中的信息量/差异化/可复制由 **AI 强模评分**（与写 recommend 同批产出）；③ 用 `merge_batch_scores.py` 合并——它**只写 info/diff/copy/total 四字段并保留 signal_strength**，按上面公式算 total 并封顶。评分写回的是候选文件。

**推荐理由（recommend）写法**：
- 用**自然流畅的一段话**，把信息量/差异化/可复制三方面的判断融进去讲（信号强度已在徽章展示，不复述）。**禁机械式"信息量：xxx；差异化：xxx；可复制：xxx"三段式。**
- 与 description 分工：**description 讲"它是谁、做什么"（事实），recommend 讲"为什么值得写"（判断）**，两者不重复。
- 写完自检：卡片已展示的结构化信息（融资金额、轮次、标题、日期等）recommend 里不再复述。
- 要有洞察（为什么这家值得写），不写死规则套话。

> **"三维是否有真判断"由步骤 7 关卡 2 子智能体做语义检查**（看实质，不看有没有出现那几个词）。

### 3.5 步骤 6 · 前端展示校验

跑 `gen_enterprise.py` 生成，肉眼检查卡片。**有值才渲染，空值一律隐藏。**

| 展示字段 | 位置 | 说明 |
|---|---|---|
| name + name_cn | 头部 | 中文名优先 |
| tag_l2 | 头部标签栏 | 只展示二级标签 |
| total_score | 头部徽章 | 0~10 存储，前端 ×10 取整封顶 100；hover 显四维 |
| description | 主体 | 中文介绍（主字段） |
| recommend | 主体 | 推荐理由 |
| funding_latest / funding_total | meta | 需含数字才显示；金额 `norm_amount` 转 M→万/B→亿、留币种 |
| investors / payor_model / founded / website_url / crunchbase_url | meta | 有值才显示 |
| 🔥 徽标 | 头部 | 非媒体企业且 30 天内被报道 |
| 近期动态/报道、deep_article_links | 底部 | 有值才显示 |

**不再展示**：highlights（与 description 重复）、business_tags（雷同高）、tag_l1/category_*（只留 tag_l2）、region（太粗）、source、competitors（数据空）、events、business_model。

**排序**：可切换 动态↓/评分↓/融资↓；**评分一律用 total_score（×10 显示分制），不用旧 research_value**。默认列表：`last_news_map` 四来源 → 有动态排前 → 同日按评分高 → 无动态按评分高。

### 3.6 步骤 7 · 质量校验（三道关卡）

**关卡 1 · 门禁脚本**（一次跑完，纯脚本不耗积分）：

Description 门禁（`check_description.py`，D1–D4）：

| 编号 | 检查 | 实现 |
|---|---|---|
| D1 | 非空且 ≥20 字 | `len(strip) >= 20` |
| D2 | 非纯英文 | 中文字符 > 总长×30% |
| D3 | 禁 BANNED 模板句 | 复用 check_single 的 BANNED + 正则 |
| D4 | 无原始标记残留 | 检测【提供资源】等 |

Recommend 门禁（`check_single.py`，唯一正式门禁）：

| 编号 | 检查 | 实现原理 |
|---|---|---|
| R1 | 单字符串 | 类型检查 |
| R2 | 字数 20–200 | 去空格字符数 |
| R3 | 禁模板套话 | BANNED 列表(60+条)子串 + 正则(15条) |
| R4 | 禁出现企业名 | name/name_cn 子串检测 |
| R-redundancy | 禁复述列表字段 | 融资数字取交集 / 阶段词交叉 / 与 description 4-gram Jaccard>0.65 |
| R-noabs | 禁绝对化用词 | ABSOLUTE 列表(20条，如"市场空白") |
| R-jargon | 禁技术黑话 | JARGON 列表(16条，如 CNS/VBC/DRG) |
| R-filler | 禁废话填充 | FILLER 列表(8条，如"赋能/闭环") |
| R10 | 跨企业雷同度>0.5 | 两两 recommend 做 LCS≥15 且 字符集 Jaccard>0.5 判雷同。**纯脚本、不调模型、零积分**，全库约 1~3 秒，只报不改 |

> 硬性规则（如字数）只在门禁写一处，走查 prompt 不重复写阈值，避免两处改丢冲突。

**关卡 2 · 子智能体语义走查（循环 ≤2 轮）**：派 general-purpose 子智能体，指令要点——
> 你是企业库质量走查员，检查这批新企业：
> 1. **description + recommend 一起查**：description 是否中文为主、说清三件事、有无模板套话、与 recommend 是否重复；recommend 是否过门禁（非空/非套话/不雷同/有真判断/不复述基本事实）；
> 2. **三维真判断（这是唯一防线）**：recommend 是否真给出了信息量（素材够不够挖）、差异化（独特在哪）、可复制（国内能学什么）的有据判断——**看实质内容，不看有没有出现那几个词**；
> 3. 银发信号判定是否合理；4. 字段是否齐全（尤其 description/source/ingest_time）；5. tag_l2 是否在 `_l2_l1.json` 词表中。
> 输出问题清单（企业名 + 字段 + 问题 + 建议）。

规则：**最多 2 轮**；每轮之间**主智能体（你）负责修**，不是子智能体自己改；2 轮后仍有问题标"待小爽定"进步骤 8；description 与 recommend 合并在一次调用里查。

**关卡 3 · 自己再过一遍**：打开预览表逐行看，确认子智能体发现的问题已修、字段齐全、格式正确。

### 3.7 步骤 8 · 小爽审核（人工硬卡点）

发**全字段预览表 Excel**（不只核心几列，按重要程度排序），至少含：serial / name / tag_l2 / description(全文) / recommend(全文) / signal_strength / info_score / diff_score / copy_score / total_score / funding_latest / funding_total / investors / payor_model / founded / stage / region / website_url / deep_article_links / news_coverage / **银发信号判定(通过/拒绝+理由)** / **去重结果(新/已存在/疑似)** / ingest_time / update_time / source。

> 预览表 Excel 目前手工/半手工生成（自动生成工具待建，见 §7 第 9 项）；生成方式：从候选文件按上面列顺序导出。

**审核附言（必写，附在表格后，三点，没有就写"无"）**：
1. **遇到的问题**：表格里看不出来的（如某两家疑似重复但证据不足、某家融资两来源矛盾）；
2. **需要协助的**：需小爽拍板/提供信息的点（如某家算不算银发、某信源要不要转正）；
3. **建议**：流程/体系层面的（如建议新增某二级标签）。

> **别和 §5.1 第 5 步的"收尾必给三样"搞混**：**审核附言**是步骤 8 随预览表发的、只针对本批数据；**收尾三样（需拍板项/下一步/建议）**是整个任务结束汇报时发的、针对整轮工作。

**等小爽确认"可以入库"才进下一步。**

**驳回处理**（驳回 ≠ 从头再来，只修有问题的）：

| 问题类型 | 处理 |
|---|---|
| 个别企业信息有误 | 改字段→重跑门禁→更新预览表→重交该企业 |
| 多家共性问题 | 批量改→全部重跑门禁→更新→重交 |
| 规则理解分歧 | 给出你的判断+理由，交小爽拍板 |
| 流程性问题 | 记录，本轮先继续，收尾时更新手册 |

修完后**另派一个子智能体复核**（不算 2 轮走查限额内），确认无误再部署。

### 3.8 步骤 9 · 合并部署

**首选一条命令**：
```
python scripts/enterprise_build.py --candidates 候选.json --merge --deploy
```
串联：门禁复跑（check_single + check_description + R10）→ `all_enterprises.json` 自动 `.bak` 备份 → 按 serial **增量合并**（只更新候选字段）→ `gen_enterprise.py` + `generator.py` 重生成 → `deploy_ghpages.py` 部署。
- **默认不带 `--deploy`**（步骤 8 放行后才加）；不带 `--merge` 则只做门禁自测。

手动分步（出问题时定位用）：①直接编辑 `all_enterprises.json`（`merge_manual_enterprises.py` 写旧字段 `category_*`，**新入库勿用**）；②跑 `gen_enterprise.py` + 生成器重生成 `output/`；③`deploy_ghpages.py` 部署（Windows `\r` 污染脚本已处理，大文件进 `.gitignore`）；④`git commit` 留痕。

### 3.9 步骤 10 · 上线走查与回滚

- **走查子智能体**：上线后派 general-purpose，背景设"国内小白读者"，检查 description/recommend/银发判定/字段是否看得懂、过门禁。
- **抽查**：本次入库至少抽 5 家看渲染/排序/中文介绍。
- **回滚/自修**：上线后自查发现的技术/渲染问题，**直接改+重部署，不必逐条通知小爽**；涉及规则或数据实质变更（应已事先评审）走收尾交小爽确认，必要时回滚。严禁现场手改线上。
- **分支策略**：UI/UX 小改可先上线后补审；**评分/推荐/标签/关键商业字段必须先审后上线**。

## 第 4 节 · 协作机制（与其他 AI 怎么配合）

### 4.1 外部 AI 名单交接（名单交接制）

**职责分界**：
- **联网搜集某家企业资料**（搜索→开页面→提取）= 企业库 AI 日常能力，按需做。
- **把某个网站全部企业名录成体系爬下来**（翻页/反爬/批量结构化）= **爬虫任务**，归信源扩充 AI / 爬虫脚本，企业库 AI 不越界爬整站。
- 分工：**信源侧"发现企业、交名单"；企业库侧"判断入库、怎么入库"。**

**名单标准**：信源 AI 交来的是**企业名单**，每家至少含：
```
企业名称(必填) | 官网或来源URL(尽量) | 地区(尽量) | 银发信号初判一句话(尽量) | 已知基础信息(有就给)
```
入不入库、怎么入库由企业库 AI 全权判断（走 §2 完整流程）；信源 AI 的初判只是参考。

**接收动作**：结构化文件放 `handoff/enterprise_inbox/` → 从步骤 1 走完整流程 → 结果放 `handoff/enterprise_outbox/` → 要反馈信源 AI 的写跨 AI 笔记（§4.2）。

### 4.2 多 AI 协作共享区

**位置**：`handoff/cross_ai_notes/`（格式见目录内 README）。
**用途**：干自己活时发现别人职责内的问题/机会（如补字段时发现某站值得当信源），写一条笔记留言，不打断对方、不越界代办。
**格式**：文件名 `YYYY-MM-DD_来自XX_给_目标AI_主题.md`，头部标 `to:/from:/date:/status:`（pending→done）。
**查看**：每 AI 设周自动化跑 `python scripts/cross_ai_digest.py --ai 自己名字`，列待处理笔记 → 处理 → status 改 done → 需要就汇报小爽。企业库 AI 的周任务已建（每周一 9:00，automation-1784882846607）。

## 第 5 节 · 收尾与维护（每次任务结束照这条走）

### 5.1 任务收尾主流程（一条主线，五步）

```
1. 更新任务规划（企业库任务规划_V*.md）：完成的移"已完成"、新增登"进行中"、遗留登"待办"
2. 写 memory：.workbuddy/memory/YYYY-MM-DD.md 记本轮做了什么
3. git 提交留痕：本轮改动 commit（不一定 push）
4. 判断：本轮改了"手册规则 / 脚本代码"吗？（只改企业数据字段=日常入库，不算，不升版本）
      改了规则或代码 → 走 5.2 升级手册（含四问复盘）
      只改了数据 → 跳过第 4 步
5. 汇报小爽（固定格式）：
   · 做了什么 / 改了什么规则 / 部署了什么 / 遗留什么
   · 【沟通规范·必给三样】① 需你拍板或协作的点  ② 我的下一步计划  ③ 我的建议/想法
```

> 第 5 步的"必给三样"是小爽定的沟通规范（2026-07-24）：**回答完问题后主动给"需拍板项 + 下一步 + 建议"，不用小爽每次问。** 也见《企业库行为准则.md》。

### 5.2 升级手册版本（仅当 5.1 第 4 步触发）

```
a. 定版本号：增删步骤/流程重构/公式变 → 大版本+1（V7→V8）
            门禁值/文字/bug修/纯优化 → 小版本+0.1（V7.4→V7.5）
            纯错字格式 → 不升版本直接改
b. 写更新栏：只列"本版变了什么"；本版新增文字标 ⚡️，同时清掉上一版的 ⚡️
c. 逐节比对上一版防漏：字段表 / 门禁表 / 前端字段表这类"易漏清单"逐项核对
d. 正文洁癖（本版起硬规则）：
     · 已删除的规则不在正文保留 → 只在版本沿革记一句
     · 解释性 / 教学性 / "为什么这么改"的话 → 走对话发小爽，不进正文
     · 上一版强调用的 ⚡️ 解释文字，本版一并清掉
e. 旧版移入 _archive_企业库旧文档/；企业库运维/ 只留最新版 + 任务规划 + 行为准则
f. MEMORY.md 更新"当前最新版本号"
g. 四问复盘（下面）
```

**四问复盘**（在汇报小爽时附答案，结论落到对应层）：
```
1. 这次调整解决了什么问题？
2. 这个问题当初为什么会发生？（挖根因）
3. 为什么现在才被发现？（发现机制哪失灵）
4. 以后如何从源头避免？→ 落在哪一层：流程规则 / 门禁脚本 / 行为准则
```

### 5.3 文档 ↔ 代码一致性（随时适用的原则，不是单独流程）

- 改代码前先读手册对应节；改文档前先读对应代码。
- 发现两边不一致 → 判断哪边是"**经确认的最新正确版本**"（**代码也可能旧/错**，如 V7.3 修的排序键 bug 就是代码错文档对）；都不确定就问小爽。
- 硬规则（门禁值/评分公式等）变更 → **代码与文档同一次 commit 同步改**。
- 本轮不改的不一致 → 收尾时登记"待处理：文档代码不一致[位置]"。

### 5.4 月度归档清理

每月 7 日 23:00（自动化或手动）：`_deprecated/` 下 1 个月前确定不用的临时文件删或续归档；根目录散落临时脚本移入 `_deprecated/`（命名加 `企业库_` 前缀）。
