## 1. 网站定位

Silver Pulse（银脉）= 银发经济投融资资讯聚合 **+ 企业数据库**，本质是小爽的**"选题情报台"**——让小爽一眼看到"今天哪些企业 / 资讯值得写深度稿"。

> 它不是资讯汇编站，是给小爽自己用的**选题决策工具**。每家企业 / 每条资讯的终点问题都是：中国银发经济创业者能从中借鉴什么？

---

## 2. 网站基本情况

- **真相源（唯一数据真相）**：`data/enterprise/all_enterprises.json` —— 直接改它 = 改真相。当前约 **1773 家**、40+ 字段。
- **部署**：独立 `gh-pages` 分支（main 放代码/数据，gh-pages 只放生成的网页）。LIVE：`https://shuanghello153-eng.github.io/silver-pulse/`
- **采集（信源与资讯）**：由**信源扩充 AI** 负责（RSS-first，44 信源，海外为主）。企业库不碰采集。
- **about 页**：已下架，不再生成维护。
- **站内协作的 AI**（互不直连，通过小爽 / 数据交接 / 附录 A 共享笔记区）：
  1. **信源扩充 AI**：信源发现与资讯采集（不归你管）
  2. **企业库运营 AI（= 你）**：企业库一切维护、入库、评分、推荐理由、前端渲染、部署、文档与记忆
  - 标签体系由专门 AI 定义（你不定义新词，只在既有体系内选 1~3 写入 `tag_l2`）

## 4. 整体工作流程

### 4.1 概括介绍

所有任务走**同一套流程**，只是「从哪进、走到哪停」不同。不存在多套独立流程。

### 4.2 需求来源与分支

主要需求来源有四类（**注意：不是穷尽规则，任何临时小需求——比如 UI/UX 微调——都可走轻量分支**）：

| 来源 | 走哪条流程 | 说明 |
|---|---|---|
| **A. 小爽给企业名单** | → 新企业入库（完整 1→11 步） | 最常见 |
| **B. 每月资讯扫描发现** | → 并入 A（完整入库步） | 每月 1 日 23:00 扫描发现的新企业走完整流程 |
| **C. 存量走查发现问题** | → 从**步骤 3**起跳，跳过步骤 1–2（准入/去重已做过） | 例：英文 description 待译、模板话术待清 |
| **D. 外部 AI 交接** | → 信源扩充 AI 交来**企业名单** | 见附录 A 名单交接制 |

- **轻量分支**：纯 UI/UX 小改动（搜索框跳动、placeholder 文案等）可走「前端校验 → 直接部署 → 事后补审」，不必走完整审核关卡。

### 4.3 详细步骤（一条主流程，编号 1–11）

> 来源 C 从步骤 3 起；轻量 UI 改动可只走步骤 6→9 并事后补审，跳过 8。

1. **银发相关性判断（入库准入）** —— 无信号直接删，不进库
2. **全库去重** —— 对 `all_enterprises.json` 全量比对（先跑关键词粗筛脚本，再 AI 精比对）
3. **补全所有字段** —— 联网/翻译补齐，重点：description / 标签 / 评分键 / 商业字段（补字段时记录引用网址）
4. **写推荐理由（recommend）** —— 最便宜模型产出（见 §5.4 模型策略）
5. **算评分** —— 信号强度（脚本）＋ 四维精评
6. **前端展示校验** —— 跑生成器，肉眼看卡片渲染
7. **质量门禁自测** —— 跑门禁脚本 + 子智能体走查
8. **小爽审核** —— 发全字段预览表 + 审核附言（必写），硬卡点
9. **合并部署** —— 编辑真相源 → 生成 → 部署 gh-pages（可用编排脚本一键跑）
10. **上线走查 + 抽查** —— 派子智能体走查，问题回滚
11. **收尾** —— 更新任务规划 / 升版本（若规则变）/ 写 memory / git 提交 / 汇报小爽（含「三样」）

> 🆕【新增 V7.6】**贯穿全程的工作产物 = 候选 JSON（`候选.json`）**：步骤 1–9 你产出的新企业数据都先写进一个候选 JSON（字段同 `all_enterprises.json` 单条），门禁/预览/合并全部读它；步骤 9 才合并进真相源。它既是草稿隔离层，也是步骤 8 发给小爽预览表的数据源。格式：`[{"serial": "#XXXX", "name": "...", "description": "...", ...}, ...]`。

> ⏳（下一版本会删除）**候选 vs 真相源的执行边界（最关键，务必分清）**：`候选.json` 是你这轮的**草稿**，只在本次任务内流转；`all_enterprises.json` 是**真相源**，只有步骤 9 合并时才改。评分/门禁命令默认对 `候选.json` 跑（见 §5.4 的 `--candidates` 用法），**绝不在没合并前拿候选去改全库**。

### 4.4 流程衔接说明

#### 4.4.1 节点分类（AI 介入 vs 纯脚本）

> ✏️【调整 V7.6】原则明确化：把节点分成「AI 必须介入」和「纯脚本」。相邻纯脚本节点用编排脚本串成一条命令，AI 只在必须介入的节点动脑——AI 调用次数 = 语义判断次数。

| 步骤 | 节点类型 | 衔接方式 |
|---|---|---|
| 1a 初筛 | 纯脚本 | `config.SILVER_STRONG_KEYWORDS` 强词命中 |
| 1b 二筛 | **AI 介入** | 低模是非题判断 |
| 2a 去重粗筛 | 纯脚本 | `dedup_keyword_prescreen.py` |
| 2b 去重裁决 | **AI 介入** | 对疑似候选做信息增量比对 |
| 3 补全字段 | AI 为主 | 联网/翻译；引用网址顺手记录 |
| 4 推荐理由 | **AI 介入** | 最便宜模型产出 |
| 5 评分 | 纯脚本 | `signal_strength.py` + `merge_batch_scores.py` |
| 6 前端生成 | 纯脚本 | `gen_enterprise.py` |
| 7 关卡1 门禁 | 纯脚本 | `check_single.py` + `check_description.py` |
| 7 关卡2 走查 | **AI 介入** | 子智能体语义走查（≤2 轮） |
| 8 小爽审核 | **人工卡点** | 预览表 + 审核附言，永不自动化 |
| 9 合并部署 | 纯脚本 | `enterprise_build.py --deploy` |
| 10 走查 | AI + 人眼 | 子智能体 + 抽查 |
| 11 收尾 | **AI 介入** | 任务规划/memory/git/汇报 |

#### 4.4.2 编排脚本 `scripts/enterprise_build.py`

```
用法：
  python scripts/enterprise_build.py --candidates 候选.json            # 门禁自测（不合并）
  python scripts/enterprise_build.py --candidates 候选.json --merge    # 门禁→备份→增量合并→生成
  python scripts/enterprise_build.py --candidates 候选.json --merge --deploy  # 以上 + 部署
串联：check_single + check_description + R10 → all_enterprises.json 自动 .bak → 按 serial 增量合并 → 生成 →（--deploy）部署
```

**质量不受影响**：串联的全是确定性节点；语义节点（二筛/写作/走查/审核）仍由 AI/小爽把关。**默认不带 --deploy**，步骤 8 放行后才加部署参数。

#### 4.4.3 流程不会卡住的保障

- **脚本报错** → 看报错修数据，重跑
- **AI 判断拿不准** → 标记「待小爽定」，进步骤 8 让小爽拍板，**不阻塞其他企业**
- **子智能体超时/差** → 换 prompt 表达，或自己先做一遍再让它复查
- **小爽驳回** → 见步骤 8 驳回流程
- **关键设计**：单家不阻塞批量（一批 20 家有 3 家争议，先推 17 家，3 家「待定」）

### 5.2 步骤 2 · 全库去重

**比对对象必须是全库 `all_enterprises.json`**

#### 2.1 脚本粗筛（已建：`scores_draft/rework/dedup_keyword_prescreen.py`）

每次入库先跑：
```
python scores_draft/rework/dedup_keyword_prescreen.py --name "北京乐龄养老科技有限公司"
python scores_draft/rework/dedup_keyword_prescreen.py --candidates 候选.json
```
原理：去括注 → 去 ~60 公司后缀 → 去 ~90 城市国家前缀 → 循环剥离出核心词 → 全库 name/name_cn 双向子串匹配 → 输出疑似重复候选。纯脚本零积分。

#### 2.2 精确匹配 + 模糊裁决

| 情形 | 处理 |
|---|---|
| **一致**（信息无差异） | 跳过，不新建 |
| **增量**（相似但信息有补充） | 合并进已有记录，补增量字段；拿不准标「待小爽定」 |
| **冲突**（疑似同家但业务矛盾） | 联网复核，以证据为准；交小爽裁决 |

> 🆕【新增 V7.6】**模糊相似度判定口径（澄清）**：
> - 「乐龄圈」「康乐龄」「北京乐龄养老科技有限公司」= **3 家不同企业**（核心词都含「乐龄」但主体不同，不合并）。
> - 「福寿康」「上海福寿康xx」「昆明福寿康xx」= **1 家企业**（各地分公司，合并进总部记录）。
> - 模糊相似度最终由 AI 校验（步骤 2b），拿不准标「待小爽定」。

### 5.3 步骤 3 · 补全所有字段

联网 / 翻译补齐字段字典（附录 C）里所有在使用的字段，尽量都补齐。

- **必填最低门槛**：`serial` / `name` / `region` / `description(≥20字)` / `source` / `ingest_time` / `update_time`。
- **补不到** → 标 **「待补充」**，**禁止编造**。
- **`serial`**：格式 `#XXXX`，取现有最大值 +1。
- **重点字段**：
  - **description**：中文、≥20 字、说清「做什么 / 服务谁 / 怎么赚钱」；禁模板套话、禁英文主导、禁夹带原始标记；单位用中文（万/亿）。
  - **标签 `tag_l2`**：从 `data/enterprise/_l2_l1.json` 现有体系选 1~3，不自造新词；打标时顺便校验 `tag_l2` 是否在词表，不在即报警。
  - **评分键 / `funding_*` / 动态时间**：一并补齐。
- **搜索索引** = `name`(+name_cn) + `description` + `tags`(+同类词) + `stage` + `recommend`。

#### 3.1 引用网址记录与渠道去重（已建：`scripts/collect_source_urls.py`）

**目的**：补字段时反复用的网站，可能就是值得转正的信源——自动化这个过程。

- 记录：补字段时把引用过的网址正常写入字段（website_url / crunchbase_url / source_urls / reference_urls 等），不用额外操作。
- 统计脚本：`python scripts/collect_source_urls.py`（可加 `--min N`），做三件事：

### 5.4 步骤 4 + 5 · 评分与推荐理由

#### 模型策略（✏️【调整 V7.6】按小爽 07-24 定）

> **所有 AI 判断统一用最便宜模型**（当前 HY3 免费可用）。国内 / 海外来源同等重要，**不因省钱过度牺牲质量**；若某节点最便宜模型质量明显不够，可升级但需在汇报里说明。

#### 评分架构

- **阶段 3 · 信号强度（脚本，零模型成本）**：`selection/signal_strength.py` 的 `compute_signal_strength(article)` 是一个**纯函数**，输入资讯 dict（含 `title`/`summary`/`date`），输出 0~10。它本为「资讯」设计；**企业评分时，把该企业最新一条融资 / 大事件拼成同样的 article dict 喂进去**，即得该企业的 `signal_strength`（0.5 保底、10 封顶）。即企业信号由「其最新动态」推导，不是凭空给。
- **阶段 4 · 四维精评（最便宜模型）**：输出 `recommend` + 四维 `info_score`/`diff_score`/`copy_score`。

**四维公式（代码 `merge_batch_scores.py:66-73`）**：
```
total_score = 信号强度 × 30% + 信息量 × 30% + 差异化 × 20% + 可复制 × 20%
```
**封顶铁律**：每维 0~10；total 0~10；**前端显示 ×10 封顶 100**。

> 🆕【新增 V7.6】**评分怎么跑（边界最关键，防污染真相源）**：
> - **正常入库**：评分**不在合并前对全库跑脚本**。你在「生产候选」这一步就把 `signal_strength` / `info_score` / `diff_score` / `copy_score` / `total_score` **直接算好写进 `候选.json` 对应字段**；`scripts/enterprise_build.py` **不含评分步骤**，只把你算好的分合并进真相源。顺序永远：**先算分 → 再合并**。
> - **这两个脚本的真实用途是「全库重跑」**（不是入库步骤，DB 级操作，勿在入库一轮里对全库跑）：
>   - `merge_batch_scores.py`：读 `scores_draft/rework/batches_score/batch_*.json`（AI 批量产出的四维结果），写回 `all_enterprises.json` 的 recommend / 四维 / total。**只在公式或权重变了、要重算全部 1773 家时跑。**
>   - `selection/signal_strength.py`：无 CLI，只能 `import` 当函数用（服务于资讯评分 `score_and_merge.py` / `backfill_signal_strength.py`）。企业信号请用上面「拼 article dict 喂函数」方式，不要 `python ... signal_strength.py --input ...`（脚本无该参数，且它是资讯口径）。
>
> ⏳（下一版本会删除）初版草稿曾误写 `python signal_strength.py --input all_enterprises.json` 这类命令——经子智能体走查发现两脚本均无该参数，且对全库跑会污染真相源，已据实修正为「候选内算分 + 全库重跑分离」。下版清理此解释句。

**推荐理由（recommend）写法**：
- 一段自然流畅的话，把信息量 / 差异化 / 可复制融进去讲，不分段、不逐维列。
- 自检：卡片已展示的结构化信息（融资/轮次/标题）推荐理由里不复述。
- 与 description 分工：description 讲「是谁、做什么」（事实），recommend 讲「为什么值得写」（判断）。
- **禁止**机械式「信息量：xxx；差异化：xxx」三段式——R5 门禁已删正是为此，三维真判断由关卡 2 子智能体语义走查负责。
