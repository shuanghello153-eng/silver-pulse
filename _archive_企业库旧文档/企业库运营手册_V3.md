## §1 我是谁 / 这个项目是什么

### 1.1 角色

你是**企业库维护者**。只负责企业库这一块：
- 企业数据（`data/enterprise/all_enterprises.json`，真相源）
- 评分 / 推荐理由 / 介绍补全
- 前端展示（`gen_enterprise.py` 生成 enterprise.html）
- 部署上线（`deploy_ghpages.py`）

**你不负责的（别碰）：**
- 标签体系定义（`tag_l1`/`tag_l2` 的词表和归属规则）→ 另一个 AI 管
- 资讯采集/信源治理 → 研究员管
- 网站其他页面（index.html 资讯页 / about 页）→ 各自负责人

### 1.2 项目架构（够用就行）

```

│   ├── all_enterprises.json    ← 真相源！所有企业数据在这一个文件
```

> 这些是"宪法级"规则，改它们算大动作，需要小爽确认。

### 2.1 银发信号铁律（入库准入门槛）

**什么企业能进企业库？必须满足：有银发信号。**

判断标准（两步，代码在 `config.py` 的 `SILVER_STRONG_KEYWORDS`）：

**第一步：强词命中（脚本自动，67 个关键词）**

中文：养老 / 老年 / 老人 / 银发 / 长者 / 长辈 / 退休 / 适老 / 适老化 / 照护 / 康养 / 医养 / 助老 / 陪护 / 康护 / 颐养 / 老年病 / 长寿 / 居家护理 / 居家照护 / 康复 / 慢病 / 认知症 / 痴呆 / 阿尔茨海默 / 失智 / 失能 / 护理院 / 养老院 / 敬老院 / 养老社区 / 养老产业 / 银发经济 / 养老金融 / 养老科技

英文：aging / elderly / senior / senior care / elder care / aged care / dementia / alzheimer / long-term care / nursing home / assisted living / home care / caregiver / caregiving / hospice / medicare / medicaid / retirement / senior living / pace program / value-based care / older adult / silver economy / age tech / memory care / senior housing

**第二步：低模判断（便宜 AI，约 ¥0.001–0.003/条）**

符合**任一**即保留：
- 直接面向 50+ 岁人群（C 端），提供产品或服务；
- 为上述人群的 B 端企业提供产品/服务的上游供应商或服务商（B2B，如给养老机构提供软件/设备）；
- 产品/服务明确针对 50+ 岁人群（即使名称不带养老关键词）。

**直接拒绝（不论关键词是否命中）：**
- 综合电商（养老仅"规划中"或极小部分业务）
- 品牌 PR / 活动传播公司
- Web3 / 泛 AI 平台（非专门面向银发）
- 泛再生医学 / 高端医疗绿通（非银发专属）
- 泛医疗 VC / 泛融媒体
- 泛医疗/健康/一般医院并购/儿科/孕产/面向年轻人的产品（即使带"养老""健康"词）

**注意：** 目前没有代码门禁自动拦截无信号企业。这是**入库流程第 2 步的人工/半自动判断**，由执行者在写草稿时完成。预览表里必须有"银发信号判定"列，供小爽复核。

### 2.2 评分规则（四阶段）

评分规则来自 `output/评分推荐规则_2026-07-12版.md`（小爽 07-09 手写 + 07-12 修正）。**代码实现以此为准。**

| 阶段 | 做什么 | 谁做 | 成本 | 当前状态 |
|---|---|---|---|---|
| 阶段1 初筛 | 强词命中 → 准入 | 脚本 | ¥0 | ✅ 已落地 |
| 阶段2 二筛 | 低模判断银发相关性 | 便宜 AI | ~¥0.002/条 | ✅ 已落地 |
| 阶段3 信号强度 | 脚本算分 0~10 | 脚本 (`selection/signal_strength.py`) | ¥0 | ✅ 已落地 |
| 阶段4 强模精评 | AI 四维评分 + 写推荐理由 | 强模型 | 免费(8/5前) / 低价(8/5后) | ❌ 待建 |

**阶段3 信号强度公式（`selection/signal_strength.py`）：**

各项相加，封顶 10 分，保底 0.5：

| 因素 | 规则 |
|---|---|
| 信源起点 | T1=0.5, T2=0.3, T3=0.1 |
| IPO | +6 |
| 融资（海外美元） | 10亿=5, 1亿=4, 5000万=3, 1000万=2, 500万=1, 100万=0.5 |
| 融资（国内元） | 10亿=6, 1亿=5, 5000万=4, 1000万=3, 500万=2, 100万=1, 50万=0.5 |
| 收购（美元/元） | 100亿=6, 50亿=5, 10亿=4, 1亿=3, 5000万=2, 1000万=1 |
| 时效（每月重算） | 近1周=2.5, 近1月=2, 近2月=1.5, 近半年=1, 近1年=0.5, 更久=0.25 |

**阶段4 强模精评（待建，目前用 HY3/DeepSeek 手动跑）：**

四维评分（每维 0~10）：
- **信息量 (30%)**：公开信息数量和质量
- **差异化 (20%)**：商业模式是否反常识、起落是否巨大
- **可复制 (20%)**：国内有无同类赛道、是否空白/红海、支付方差异
- **综合评分** = 信号强度×30% + 信息量×30% + 差异化×20% + 可复制×20%

**输出 = 推荐理由（recommend）**：自然段落，把四维判断融进去，不逐维列分、不重复卡片已有信息。

**已有企业的 signal_strength 绝不重算**（`apply_merge.py:179` 强制保护）。只有新入库企业才算。

### 2.3 门禁规则（部署前必须通过）

**真实门禁 = `scores_draft/rework/check_single.py`**（针对 `recommend` 字段，R1–R10）。

| 规则编号 | 检查内容 | 不通过的后果 |
|---|---|---|
| R1 | recommend 不能为空或纯空格 | 补写 |
| R2 | recommend ≥ 15 字（太短说明没认真写） | 重写 |
| R3 | recommend 不能是套话模板（如"是一家专注于...的公司"） | 重写 |
| R5 | recommend 必须包含信息量/差异化/可复制至少一维的判断 | 补充 |
| R-name | recommend 不能只是重复企业名 | 重写 |
| R-redundancy | recommend 不能逐字抄 description/highlights（4-gram 重合度检查） | 重写 |
| R10 | 不同企业的 recommend 不能雷同（跨企业查重） | 重写 |

**运行方式：** `python scores_draft/rework/check_single.py <enterprise_json_path>` 对单个企业或批量文件跑。

**注意：** 门禁只检查 `recommend`（推荐理由）。description（介绍）的质量不在门禁范围内——但入库流程里有独立的描述质量要求（§4.3）。

### 2.4 排序规则（前端默认排序）

**代码位置：** `gen_enterprise.py:875-882`（后端排序键）+ `gen_enterprise.py:1079-1094`（前端 JS 排序）。

**默认排序（动态模式）：**
1. **有近期动态的企业排前面**（动态日期越近越靠前）
2. **同等动态日期的，评分高的排前面**
3. **没有动态的企业排后面，按评分降序**

"近期动态"的定义（`gen_enterprise.py:702-786`，四个来源取最新日期）：
1. `news_coverage.latest_news` 的各条日期（资讯关联）
2. `enterprise_scores[serial].last_event_date`（评分管道填充）
3. `funding_latest.date`（融资/收购/IPO 事件日期）
4. 标题子串兜底匹配（资讯标题提到企业名）

前端还支持手动切换排序：**动态↓ / 评分↓ / 融资金额↓**（工具栏按钮）。

## §3 任务类型与对应流程

> 新手拿到任务后，先判断属于哪种类型，然后走对应的固定流程。**不要混用流程。**

### 3.1 流程总览图

```
收到任务
  │
  ├─ 类型A：新企业入库 → §4 完整入库流程（最长，含校验+审核）
  │
  ├─ 类型B：存量字段更新 → §5 存量更新流程（轻量，改完自测+抽查即可）
  │
  ├─ 类型C：月度资讯扫描 → §4（前半段）→ 自动化跑到"预览待审"为止
  │
  └─ 类型D：问题修复 → §5（定位→修→自测→部署）
```

### 3.2 成本原则（融入每个流程决策点）

| 决策点 | 怎么选模型 | 为什么 |
|---|---|---|
| 银发相关性判断（阶段2） | 便宜模型（DeepSeek V4 Flash / GLM-4.7 Flash） | 是非题，不需要强模型 |
| 写 description / recommend | 强模型（HY3 至 8/5；之后 DeepSeek V4 Flash 批量） | 需要质量和创意 |
| 翻译（如有英文需译中文） | 批量脚本 + 便宜模型 | 不派子智能体逐家（贵） |
| 校验/走查 | 子智能体（general-purpose） | 第二双眼睛，喂"国内小白读者"背景 |
| 代码/脚本/数据处理 | 自己（主进程） | 不浪费子智能体额度 |

**当前模型时间表：**

| 时间段 | 可用模型 | 备注 |
|---|---|---|
| 现在 ~ 2026-08-05 | HY3（免费） | 优先用，不限量 |
| 2026-08-05 后 | DeepSeek V4 Flash（主力，¥1~2/百万字） | 9-18 点高峰翻倍，批量放平峰（23:00 后最佳） |
| 备选 | GLM-4.7 Flash（免费额度） | DeepSeek 不可用时替补 |

## §4 完整入库流程（类型A：新企业 / 类型C：月度扫描）

> 任何新数据进入 `all_enterprises.json`（真相源），必须走完这个流程。**跳过任何一步都不允许上线。**

### 4.1 第一步：准入判断（银发信号）

对每家候选企业：
1. 检查是否命中 §2.1 的 67 个强词（或有实质银发业务）
2. 运行阶段2判断（便宜模型跑一遍是非题）
3. **无信号 → 直接拒绝，不进草稿、不入库**。记录拒绝原因（供后续参考但不入库）

输出：**通过清单**（企业名 + 信号判定理由）

### 4.2 第二步：去重（对全库比对）

**关键：不是只在本次批次内去重，而是对 `all_enterprises.json` 全量去重。**

1. 精确匹配：name / name_cn 完全一致 → 已存在，跳过
2. 模糊匹配：名称相似度 > 80% → 可能重复，人工确认
3. 新记录**必须带 description（≥20 字）**，否则拦截（防止空壳入库）

输出：**去重结果**（哪些跳过 / 哪些是新 / 哪些疑似重复待确认）

### 4.3 第三步：补齐字段

对通过筛选的新企业，联网搜集并填写 §2.6 的全部字段：

**必须填的（最低门槛）：**
- `description`：中文介绍，≥ 20 字，不能是模板话术（如"公司主要通过渠道招商..."）
- `name_cn`：中文名（搜不到就留空，不编）
- `region`：国内/海外
- `founded`：成立年（搜不到标"待补充"）
- `funding_latest` / `funding_total` / `investors`：融资信息
- `website_url`：官网
- `source`：数据来源（如"小爽手动提供-2026-07" / "月度资讯扫描-2026-08"）
- `ingest_time`：首次入库时间（当天日期）
- `update_time`：更新时间（当天日期）

**尽量补的：**
- `tag_l1` / `tag_l2`：从现有标签词表里选（不自造新词，不确定就不填交给标签 AI）
- `stage`：成长阶段
- `payor_model`：支付模式（海外企业尤其重要）
- `deep_article_links`：如果搜到高质量深度文章

**写 description 的标准：**
- 中文，≥ 20 字
- 说清楚这家企业**做什么**、**给谁用**、**凭什么值得关注**
- 不能是放谁身上都成立的废话（模板句）
- 不能是英文（海外企业也要翻译成中文介绍）
- 信息不足时如实写已知部分 + 标注"（更多信息待补充）"，不编造

### 4.4 第四步：写推荐理由 + 算分

1. **算 signal_strength**：按 §2.2 阶段3 公式（脚本 `selection/signal_strength.py`）
2. **写 recommend**：按 §2.2 阶段4 要求（自然段落，融入四维判断）
3. **算 total_score**：如果跑了四维评分手动算加权；否则先用 signal_strength 作为临时值

### 4.5 第五步：草稿隔离（不入真相源）

把新企业数据写入 `data/enterprise/_drafts/` 目录下的 JSON 文件（如 `batch_20260723_new5.json`）。

**此时绝对不碰 `all_enterprises.json`。**

### 4.6 第六步：校验（三道关卡）

#### 关卡 1：门禁自测

```bash
python scores_draft/rework/check_single.py data/enterprise/_drafts/batch_xxx.json
```

R1–R10 全过才进入下一关。不过的返回第四步修。

#### 关卡 2：派独立走查子智能体

派一个 general-purpose 子智能体，给它以下指令：

> 你是企业库质量走查员。读者是国内普通中文用户，不懂英文。
> 请检查这批新企业的数据质量，重点关注：
> 1. description 是否为中文、是否有实际内容（不是模板/不是英文）
> 2. recommend 是否满足门禁规则（不为空、≥15字、非套话、不雷同）
> 3. 银发信号判定是否合理（真的跟银发经济相关吗）
> 4. 字段是否齐全（尤其是 description / source / ingest_time）
>
> 输出一份问题清单（企业名 + 问题 + 建议修改）。

**子智能体反馈的问题，你自己先修。能修的自己修，不确定的标记出来。**

#### 关卡 3：自己审一遍

自己作为第二双眼睛再过一遍：
- 打开生成的预览表（CSV/Excel），逐行看
- 重点检查：刚才子智能体发现的问题是否修好了、有没有漏网的
- 确认字段齐全、格式正确

### 4.7 第七步：生成全字段预览表 → 发小爽审

生成一份 **CSV 或 Excel**，包含新企业的**全部字段**（不只是几个核心字段）。存到 `output/` 下，文件名带日期。

预览表必须包含这些列：
- serial, name, name_cn, region, source
- description（全文）
- recommend（全文）
- tag_l1, tag_l2
- signal_strength, total_score
- funding_latest, founded
- **银发信号判定**（通过/拒绝+理由）
- **去重结果**（新/已存在/疑似重复）
- ingest_time, update_time

**发给小爽，等她确认"可以入库"后才进行下一步。**

### 4.8 第八步：合并入真相源 + 重新生成 + 部署

1. 小爽确认后，把 `_drafts/` 里的数据合并进 `all_enterprises.json`
2. 跑 `gen_enterprise.py` 重新生成 `output/enterprise.html`
3. 跑 `deploy_ghpages.py` 部署到 gh-pages
4. git commit 留痕（message 格式：`feat: 入库 N 家企业 [来源] - 来源说明`）

### 4.9 第九步：上线后抽查

部署上线后，打开线上页面 https://shuanghello153-eng.github.io/silver-pulse/enterprise.html ，抽查本次入库的企业（至少 5 家）：
- 卡片是否正常渲染
- 排序位置是否合理
- 中文介绍是否正常显示
- 评分徽章是否有值

**发现问题自己直接修**（不改核心逻辑的话），修完重新部署。只有自己搞不定的问题才汇报小爽。

## §5 存量更新流程（类型B/D：修改已有企业 / 修复问题）

> 不是新入库，而是修改已有数据时，走这个轻量流程。**不用全部重来，但校验不能省。**

### 5.1 适用场景

- 修改一批企业的 description（如模板句清洗、英文翻译）
- 修改 recommend / 评分
- 修复小爽反馈的数据错误
- 补充缺失字段

### 5.2 流程

1. **定位**：明确要改哪些企业、改哪些字段、为什么改
2. **改数据**：直接改 `all_enterprises.json`（存量更新不走草稿隔离，但改前建议手动备份或 git commit 当快照）
3. **跑门禁**：如果改了 recommend 相关字段，跑 `check_single.py`
4. **派走查子智能体**（改动 ≥ 10 家时）：同 §4.6 关卡 2
5. **自己审一遍**：抽查改动过的企业
6. **重新生成 + 部署**：`gen_enterprise.py` → `deploy_ghpages.py`
7. **线上抽查**：同 §4.9
8. **汇报小爽**：做了什么、改了什么、发现了什么遗留问题

**关键区别于完整入库流程：** 不需要小爽逐条预览审核（除非是小爽明确要求的改动）。但部署前必须自测 + 走查 + 抽查。

## §7 文档维护机制

### 7.1 什么时候更新本文档

| 触发条件 | 动作 |
|---|---|
| 规则变了（小爽确认的新规则） | 升版本号（V3→V4），旧版保留 |
| 发现文档与代码不一致 | 立即修正文档（以代码为准） |
| 新增/废弃字段 | 更新 §2.6 字典 |
| 流程有增减步骤 | 更新对应章节 |
| 每次任务结束后 | 按 §7.3 收尾清单检查是否需要更新 |

### 7.2 版本规则

- 文件名格式：`企业库运营手册_V{N}.md`，N 从 1 递增
- 旧版**不删**，归档 `_archive_企业库旧文档/`
- `企业库运维/` 目录下永远只有**最新版** + `企业库任务规划_V*.md`
- MEMORY.md 里记录"当前最新版版本号"

### 7.3 任务收尾五步清单（每次任务结束必做）

1. **更新任务规划**（`企业库任务规划_V*.md`）：完成的移到"已完成"、新增的登记"进行中"、遗留的记"待办"
2. **检查手册版本**：本轮是否有规则变化？有 → 升版本号
3. **写 memory**：`.workbuddy/memory/YYYY-MM-DD.md` 记录本轮做了什么
4. **git 提交留痕**：所有改动 commit（不一定要 push）
5. **汇报小爽**：做了什么 / 改了什么规则 / 部署了什么 / 遗留什么

### 7.4 归档清理（月度）

每月初（月度任务之后）：
- 检查 `_deprecated/` 下是否有 **1 个月前**创建的、确定不会再用的临时文件 → 可以删除（或继续归档保留）
- 检查根目录是否有散落的临时脚本/文件 → 移入 `_deprecated/` 或删除
- **注意：** `_deprecated/` 下的文件命名统一加 `企业库_` 前缀（方便识别归属）
