## 1. 网站定位

Silver Pulse（银脉）= 银发经济投融资资讯聚合 **+ 企业数据库**，本质是小爽的**"选题情报台"**——让小爽早上打开网站，一眼看到"今天哪些企业 / 资讯值得写深度稿"。未来可能对外开放。

> 它不是资讯汇编站，是给小爽自己用的**选题决策工具**。每家企业 / 每条资讯的终点问题都是：中国银发经济创业者能从中借鉴什么？

## 2. 网站基本情况

- **部署**：独立 `gh-pages` 分支（main 放代码/数据，gh-pages 只放生成的网页，两者分离互不污染）。LIVE：`https://shuanghello153-eng.github.io/silver-pulse/`

  1. **信源扩充 AI**：信源发现与资讯采集（不归你管）
  2. **企业库运营 AI（= 你）**：企业库一切维护、入库、评分、推荐理由、前端渲染、部署、文档与记忆

**你是企业库的唯一维护者。** 企业库的**数据 + 前端渲染 + 部署**全部由你负责，**所有字段你都要维护**（只读 / 废弃字段除外，见附录 6.1）。

## 4. 整体工作流程

### 4.1 概括介绍

所有任务走**同一套流程**，只是"从哪进、走到哪停"不同。不存在三套独立流程，不要抄三遍。

### 4.2 需求来源与分支

主要需求来源有三类（**注意：这不是穷尽规则，任何临时小需求——比如 UI/UX 微调——都可以走轻量分支，不必写死**）：

| 来源 | 走哪条流程 | 说明 |
|---|---|---|
| **A. 小爽给企业名单** | → 新企业入库（完整 1→10 步） | 最常见 |
| **B. 每月资讯扫描发现** | → 并入 A（新企业入库完整步） | 每月扫描发现的新企业走完整入库流程 |
| **C. 存量走查发现问题** | → 从**步骤 3（补全字段）**起跳，跳过步骤 1–2（准入/去重已做过） | 例：英文 description 待译、模板话术待清、漏打标 |

- **轻量分支**：纯 UI/UX 小改动（搜索框跳动、placeholder 文案等）可走"前端校验→直接部署→事后补审"，不必走完整审核关卡（见 5.9）。

### 4.3 详细步骤（一条主流程，编号 1–10）

> 来源 C 从步骤 3 起；轻量 UI 改动可只走步骤 6→9 并事后补审。

1. **银发相关性判断（入库准入）** —— 无信号直接删，不进库
2. **全库去重** —— 对 `all_enterprises.json` 全量比对
3. **补全所有字段** —— 联网/翻译补齐，重点：description / 标签 / 评分键 / 商业字段
4. **写推荐理由（recommend）** —— 强模产出
5. **算评分** —— 信号强度（脚本）＋ 四维精评
6. **前端展示校验** —— 跑生成器，肉眼看卡片渲染
7. **质量门禁自测** —— 跑 `check_single.py`
8. **小爽审核** —— 发全字段预览表，硬卡点
9. **合并部署** —— 编辑真相源 → 生成 → 部署 gh-pages
10. **上线走查 + 抽查** —— 派子智能体走查，问题回滚

## 5. 每步骤详细规则（与步骤编号一一对应）

### 5.1 步骤 1 · 银发相关性判断（入库准入）

> **定位**：这是"入不入库的门槛"，属于**相关性判断**，**不是评分**。它只产出"通过 / 拒绝"，不产出分数。绝不要把它写进"评分规则"里（V5 犯过这个错，已纠正）。

**两步法：**

- **第一步 · 强词命中（脚本自动）**：强词命中即进第二步。强词清单（约 60 个，中英文）：
  养老 / 老年 / 老人 / 银发 / 长者 / 长辈 / 退休 / 适老 / 适老化 / 照护 / 康养 / 医养 / 助老 / 陪护 / 康护 / 颐养 / 老年病 / 长寿 / 居家护理 / 居家照护 / 康复 / 慢病 / 认知症 / 痴呆 / 阿尔茨海默 / 失智 / 失能 / 护理院 / 养老院 / 敬老院 / 养老社区 / 养老产业 / 银发经济 / 养老金融 / 养老科技；英文 aging / elderly / senior / senior care / elder care / aged care / dementia / alzheimer / long-term care / nursing home / assisted living / home care / caregiver / caregiving / hospice / medicare / medicaid / retirement / senior living / pace program / value-based care / older adult / silver economy / age tech / memory care / senior housing
- **第二步 · 低模判断（便宜 AI 是非题）**：符合任一即保留——
  - 直接面向 **50 岁+** 人群（C 端）；为他们的 B 端服务提供方提供产品 / 服务
  - 面向 **医疗需求（medical needs）** 人群
  - 面向 **Medicare Advantage（美国联邦医保优势计划）参保老人**

**直接拒绝（不论是否命中强词）**：综合电商（养老仅"规划中"）、品牌 PR / 活动传播、Web3 / 通用 AI 平台、泛再生医学 / 高端医疗绿通、泛医疗 VC、泛融媒体。

> 关键词门禁是辅助，**最终以实质业务判断为准**；不确定可联网核查，默认从严（无信号即删）。

### 5.2 步骤 2 · 全库去重

**比对对象必须是全库 `all_enterprises.json`**（只比新批次内部是历史 bug 根因：曾因此出现同一家企业两条记录）。

精确匹配 `name` / `name_cn` 完全一致 → 已存在；模糊相似度 **>80%** → 疑似重复需确认。

三种结果处理：

| 情形 | 处理 |
|---|---|
| **一致**（信息无差异） | 跳过，不新建 |
| **增量**（相似但信息有补充） | 合并进已有记录，补增量字段；拿不准标"待小爽定" |
| **冲突**（疑似同家但关键业务矛盾） | 联网复核，以证据为准订正；交小爽裁决 |

**拦截铁律**：新记录必须带 `description`（≥20 字），否则拦截（防止空壳入库）。

### 5.3 步骤 3 · 补全所有字段

联网 / 翻译补齐字段字典（附录 6.1）里所有"你维护"的字段。

- **必填最低门槛**：`serial` / `name` / `region` / `description(≥20字)` / `source` / `ingest_time` / `update_time`。
- **补不到** → 标 **"待补充"**，**禁止编造**（错数据毁掉整篇公信力）。
- **`serial`**：格式 `#XXXX`，取现有最大值 +1。
- **重点字段**：
  - **description（企业介绍）**：中文、≥20 字、说清三件事——**做什么、服务谁、怎么赚钱**（信息不足至少前两件）；禁模板套话、禁英文主导、禁夹带原始标记（如【提供资源】）；单位用中文（万/亿）。
  - **标签 `tag_l1/tag_l2`**：从 `_l2_l1.json` 现有体系选 1~3，不自造新词。
  - **评分键 / `funding_*` / 动态时间**：一并补齐。

### 5.4 步骤 4 + 5 · 评分与推荐理由

> 以下为小爽 07-09 定稿、07-12 修正的评分规则，完整收录于本手册（不引用外部文档）。

**评分架构（阶段 1–2 为"银发相关性判断 / 准入"，见 5.1；阶段 3–4 为本步骤的评分）：**

- **阶段 3 · 信号强度（脚本，0~10，封顶 10 保底 0.5）**，按事件分级换算：
  - 信源起点：T1=0.5，T2=0.3，T3=0.1
  - IPO = +6；融资（海外美元）：≥10亿=5 / 1亿=4 / 5000万=3 / 1000万=2 / 500万=1 / 100万=0.5
  - 融资（国内元）：≥10亿=6 / 1亿=5 / 5000万=4 / 1000万=3 / 500万=2 / 100万=1 / 50万=0.5
  - 收购（海内外）：≥100亿=6 / 50亿=5 / 10亿=4 / 1亿=3 / 5000万=2 / 1000万=1
  - 时效：近1周=2.5 / 近1月=2 / 近2月=1.5 / 近半年=1 / 近1年=0.5 / 更久=0.25
- **阶段 4 · 强模四维精评**：输出 `recommend` + 四维评分

**四维权重公式（综合评分）：**
```
综合评分 = 信号强度 × 30% + 信息量 × 30% + 差异化 × 20% + 可复制 × 20%
```
每维 0~10。

**推荐理由（recommend）写法：**
- 用一段自然流畅的话，把**信号强度 / 信息量 / 差异化 / 可复制**四方面判断融进去讲，不刻意分段、不逐维列分。
- 写完后自检：**卡片/列表已展示的结构化信息**（融资金额、轮次、标题、摘要、来源、日期等）推荐理由里**不再重复陈述**。
- 不写"死规则"式套话；要有洞察（为什么这家值得写）。

> **铁律**：已有企业的 `signal_strength` / 历史评分**绝不重算**（除非小爽要求重跑）。

### 5.5 步骤 6 · 前端展示校验

跑 `gen_enterprise.py` 生成，肉眼检查卡片。

- **展示字段**：`name`（固定用 `name`，非 `name_cn`）、`tag_l2`、`total_score`（0~100 封顶，信号强度仅 hover）、`description`、`recommend`、投融资（`norm_amount`：M→万 / B→亿，币种保留，例 `$106M → $1.06亿`）、外链、🔥 近期动态徽标。
- **无数据不展示**：各字段各自 `if` 隐藏；空值 / "未搜到 / 未披露 / 未知" 一律隐藏。
- **不展示字段**（有值也不渲染）：`highlights` / `tag_l1` / `category_*` / `region` / `source` / `competitors` / `events` / `business_model`。
- **搜索**：索引 = `name + description + tags + stage + recommend`。
- **排序**：`last_news_map` 四来源（news_coverage / enterprise_scores.last_event_date / funding_latest.date / 标题兜底）→ 有动态排前 → 同日期评分高排前 → 无动态按评分。

### 5.6 步骤 7 · 质量门禁自测

部署前必跑 `scores_draft/rework/check_single.py`（**唯一正式门禁，针对 `recommend`**；description 质量靠走查子智能体，见 5.9）。

| 编号 | 检查内容 | 不通过后果 |
|---|---|---|
| R1 | 单字符串（非列表/非 null） | 拦截 |
| R2 | 字数 **50–240** | 拦截 |
| R3 | 禁模板套话（如"渠道招商"类） | 拦截 |
| R4 | （别名 R-name）禁直接出现企业名 | 拦截 |
| R5 | 须覆盖**三维**：信息量 / 差异化 / 可复制（不要求信号维度，融资/收购/上市已在列表展示，禁止复述） | 拦截 |
| R-redundancy | 禁复述列表已有字段（融资数字等） | 拦截 |
| R-integrity | 赛道判定与标签一致 | 拦截 |
| R-noabs | 禁绝对化用词（"最/第一/唯一"无依据） | 拦截 |
| R-jargon | 禁黑话（无必要术语） | 拦截 |
| R-filler | 禁废话填充 | 拦截 |
| R10 | 跨企业雷同度 >0.5 | 拦截 |

> ⚠️ 历史坑：V3 曾把 R2 错写成"≥15 字"、R5 错写成"至少一维"、缺多条——本版以 `check_single.py` 实际为准，前述数值为核验后正确值。

### 5.7 步骤 8 · 小爽审核

发**全字段预览表**给小爽（新企业必做；存量批量走查可免逐条预览，除非小爽要求）。**硬卡点：未确认不合并、不部署。**

### 5.8 步骤 9 · 合并部署

1. 直接编辑 `all_enterprises.json`（合并 = 编辑真相源，无自动合并脚本读草稿区；`merge_manual_enterprises.py` 写旧字段 `category_*`，**新入库勿用**）。
2. 跑 `gen_enterprise.py` + 生成器重生成 `output/`。
3. `deploy_ghpages.py` 部署（经 Git Bash；Windows 换行/`\r` 污染已脚本处理；大文件进 `.gitignore`）。
4. `git commit` 留痕（改前也先 commit 当快照，便于回滚）。

### 5.9 步骤 10 · 上线走查与回滚

- **走查子智能体**：合并前/上线后派 general-purpose 子智能体，背景设为"国内小白读者"，检查 description 是否中文有实料、recommend 是否过门禁、银发判定、字段齐全。
- **上线后抽查**：本次入库企业至少抽 5 家，看渲染 / 排序 / 中文介绍。
- **回滚 / 自修**：上线后你自查发现的技术 / 渲染类问题，**直接改 + 重新部署即可，不必逐条通知小爽**；若涉及规则或数据库实质变更（应已事先评审），走收尾流程交小爽确认，必要时回滚。严禁现场手改线上。
- **分支策略**：
  - **UI/UX 小改动**（搜索框跳动、文案等）：可先上线后补审。
  - **重要字段改动**（评分 / 推荐 / 标签 / 关键商业字段）：必须**先审后上线**。

### 5.10 行为准则（门禁自测与日常一并遵守）

- 不擅自发布任何内容（小爽是最终守门人）。
- 研究 / 运营中的敏感商业信息不外泄。
- 数据可信度 > 文笔：查不到就标"待补充"，绝不编。
- 改小爽手标必【动你标注】+ 理由；已确认决策跨轮保持。
- 独立主见：重大判断先给"我的看法 + 理由"，不把球踢回小爽。

| 坑 | 表现 | 规避 |
|---|---|---|

### 6.4 版本沿革（V1 → V7，不丢历史）

### 6.5 历史教训（写进流程）

1. 改文档不能把已定对的结论又改丢（每次新建议是叠加，不是覆盖）。
2. 清任务清单前必须先核实并登记，不得批量误清（金额万/亿、阶段4评分早已落地，曾误当摆设清掉）。
3. 文档与代码可能不一致——任务前必须核对代码，发现文档错（触发人可能是自己）要改文档。
4. 所有规则尽量融入流程带触发条件，不单独存放成死内容。
5. 写完文档跟上版校验，防漏信息。
