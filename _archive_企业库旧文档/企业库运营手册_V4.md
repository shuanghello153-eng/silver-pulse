## §0 触发机制：什么时候读这份文档

**不是"有空了看看"，而是以下情况必须先读：**

| 触发条件 | 读哪些章节 | 谁触发的 |
|---|---|---|
| 收到小爽发来的一批企业名称 / 资料，要入库 | §1 → §2（准入）→ §3（主流程）→ §4（详细规则） | 小爽 |
| 月度自动化任务启动（每月 1 日 23:00） | §1 → §3 → 跑到"预览待审"为止 | 系统闹钟 |
| 要修改已有企业的字段（介绍 / 标签 / 评分 / 任一字段） | §1 → §3（存量分支）→ §4 | 自己 / 小爽 |
| 要部署上线（git push 到 gh-pages） | §3 收尾 + §6（部署校验） | 自己 |
| 发现规则有问题要改 | §7（文档维护） | 自己 / 小爽 |
| 小爽反馈线上数据有误 | §3（存量分支 / 修复） | 小爽 |

**怎么确保一定会读？**
- 工作记忆（`MEMORY.md`）第一条就是："企业库任务前必读 `企业库运维/企业库运营手册_V*.md`（取最高版本号）+ `scores_draft/rework/check_single.py`"。每次会话开始自动注入。
- 月度自动化任务的提示词第一句就是"先读手册"。
- 如果读完发现文档本身有错或过时，**按 §7.2 修正后再动手——不要凭记忆动手**。

> **铁律·文档与代码核对（2026-07-23 新增）**
> 文档很可能跟代码不一致。每次任务前，除了读文档，还要**亲自看一眼真实代码 / 数据**确认文档说的对不对（至少核对本次任务涉及的脚本与字段）。发现文档写错 → **触发人可能是你自己**（你之前写的手册也可能过时），所以：
> 1. 文档与代码冲突时，**以代码为准**改文档，不要按错的文档动手；
> 2. 改完在 §7 收尾清单里登记"文档修正"；
> 3. 这条原则本身也要在每次任务里被执行（不是摆设）。

## §1 背景 / 角色 / 协作边界

### 1.1 我是谁（角色与职责）

你是**企业库维护者**。企业库这一块（数据 + 前端渲染 + 部署）**全部由你负责**，包括但不限于：

- **真相源数据**：`data/enterprise/all_enterprises.json` 里每一家企业的**所有字段**（身份 / 内容 / 商业 / 标签 / 评分 / 元数据），除了下面 §1.3 标"只读 / 废弃"的字段。
- **写中文介绍（description）**：海外企业也要翻译成中文介绍；英文描述、模板话术是已知旧账，按批次清洗。
- **打标签**：从**现有的二级标签词表**里给每家企业选 **1~3 个二级标签**（写入 `tag_l2`，一级 `tag_l1` 由映射自动推导，见 §4.6）。**你不负责定义词表本身**（那归标签体系负责人），但你**有打标执行权**，发现词表颗粒度问题要提建议给小爽（见 §7.3 复盘检查项）。
- **写推荐理由（recommend）**：编辑视角，过 `check_single.py` 门禁。
- **算 / 维护评分**：signal_strength / info / diff / copy / total_score（见 §4.3）。
- **前端渲染**：`gen_enterprise.py` 生成 `enterprise.html`。
- **部署上线**：`deploy_ghpages.py`。

> **注意**：V3 里写"只负责评分/推荐理由/介绍补全"是错的——那是误导，会让人以为其他字段不用管。正确说法：**企业库所有字段你都要维护**（已废弃字段除外）。

### 1.2 项目是什么（一句话）

Silver Pulse 是企业库 + 资讯看板的静态站，给小爽（银发财经作者）做**选题情报台**：一眼看到"今天哪些企业 / 资讯值得写深度稿"。

### 1.3 协作边界（谁做什么，交接在哪）

## §2 入库准入：银发信号铁律

> **为什么独立成章**：V3 把"阶段1初筛 / 阶段2二筛"塞进"评分规则"是错的——这是**银发相关性判断（入不入库的门槛）**，不是评分。评分只管阶段3/4（§4.3）。

**什么企业能进企业库？必须满足：有银发信号。**

判断标准（两步）：

**第一步：强词命中（脚本自动，67 个关键词）**
- 中文：养老 / 老年 / 老人 / 银发 / 长者 / 长辈 / 退休 / 适老 / 适老化 / 照护 / 康养 / 医养 / 助老 / 陪护 / 康护 / 颐养 / 老年病 / 长寿 / 居家护理 / 居家照护 / 康复 / 慢病 / 认知症 / 痴呆 / 阿尔茨海默 / 失智 / 失能 / 护理院 / 养老院 / 敬老院 / 养老社区 / 养老产业 / 银发经济 / 养老金融 / 养老科技
- 英文：aging / elderly / senior / senior care / elder care / aged care / dementia / alzheimer / long-term care / nursing home / assisted living / home care / caregiver / caregiving / hospice / medicare / medicaid / retirement / senior living / pace program / value-based care / older adult / silver economy / age tech / memory care / senior housing

**第二步：低模判断（便宜 AI，是非题）**
符合**任一**即保留：
- 直接面向 50+ 岁人群（C 端）提供产品 / 服务；
- 为上述人群的 B 端企业提供上游产品 / 服务（B2B，如给养老机构供软件 / 设备）；
- 产品 / 服务明确针对 50+ 岁人群（即使名称不带养老关键词）。

**直接拒绝（不论关键词是否命中）：**
- 综合电商（养老仅"规划中"或极小部分业务）
- 品牌 PR / 活动传播公司
- Web3 / 泛 AI 平台（非专门面向银发）
- 泛再生医学 / 高端医疗绿通（非银发专属）
- 泛医疗 VC / 泛融媒体
- 泛医疗 / 健康 / 一般医院并购 / 儿科 / 孕产 / 面向年轻人的产品

> **现状**：没有代码门禁自动拦截无信号企业。这是**入库流程第 1 步的人工 / 半自动判断**，由执行者在写草稿时完成。预览表里必须有"银发信号判定"列（通过 / 拒绝 + 理由）供小爽复核。判定以**实质业务**为准，关键词只是辅助；不确定联网核查，默认从严（无信号即删）。

## §3 工作流程（主流程，入口不同一套走完）

> **核心思想**：所有任务走**同一套流程**，只是"入口"不同。不要为每种任务记一套独立步骤。
> - **入口 A·新企业入库**：从 §3.1 第 1 步走到第 9 步（含小爽预览确认）
> - **入口 B·存量字段更新 / 问题修复**：从 §3.1 第 3 步起（跳过准入 / 去重，因为企业已在库），改完走 §3.3 轻量收尾（**无需小爽逐条预览**，但自测 + 走查 + 抽查不能省）
> - **入口 C·月度自动化扫描**：走 §3.1 第 1–7 步，到第 7 步"发小爽预览待审"为止，**不自动合并部署**

### 3.1 主流程九步（入口 A 完整版）

**① 准入判断（银发信号）** — 按 §2。无信号直接拒绝，不进草稿、不入库，记拒绝理由。

**② 去重（对全库比对）** — 关键：不是只在本次批次内去重，而是对 `all_enterprises.json` **全量**去重。
- 精确匹配：name / name_cn 完全一致 → 已存在，跳过
- 模糊匹配：名称相似度 > 80% → 疑似重复，人工确认
- 新记录**必须带 description（≥20 字）**，否则拦截（防止空壳入库）

**③ 补齐字段** — 联网搜集并填写字段（模板见 §4.7）。必填最低门槛：serial / name / region / description(≥20字) / source / ingest_time / update_time。其余尽力补，补不到标"待补充"不编造。

**④ 算分 + 写推荐理由** — 按 §4.3。signal_strength 算（新企业）/ 沿用（已有）；recommend 按门禁写（§4.4）。

**⑤ 草稿隔离（暂存，不碰真相源）** — 把新企业数据写入 `data/enterprise/_drafts/batch_YYYYMMDD.json`（一份供预览的副本）。**此时绝对不碰 `all_enterprises.json`。**

**⑥ 三道校验**
- **关卡 1·门禁自测**：`python scores_draft/rework/check_single.py data/enterprise/_drafts/batch_xxx.json`（R1–R10 全过才进下一关；不过回第④步修）
- **关卡 2·走查子智能体**：派 general-purpose 子智能体，背景"国内小白读者"，检查：description 是否中文 / 有实料（非模板非英文）、recommend 是否过门禁、银发信号判定是否合理、字段是否齐全。反馈的问题自己先修。
- **关卡 3·自己审**：打开预览表逐行看，确认问题修好、无漏网。

**⑦ 生成全字段预览表 → 发小爽审** — 生成 CSV/Excel（模板见 §4.7），含 serial/name/name_cn/region/source/description/recommend/tag_l1/tag_l2/signal_strength/total_score/funding/founded/银发信号判定/去重结果/ingest_time/update_time。**等小爽确认"可以入库"才进下一步。**

**⑧ 合并入真相源 + 重新生成 + 部署**
- **合并**：把 `_drafts/` 里的数据**追加进 `all_enterprises.json`**（直接编辑；编辑前先 `git commit` 一份快照）。⚠️ 没有"合并脚本"自动读 `_drafts/`——合并动作就是手动把记录加进真相源 JSON（或用 `merge_manual_enterprises.py` 但需先把它改成写 `tag_l1/tag_l2` 当前 schema，否则别用）。
- **生成**：`python gen_enterprise.py`（只生成 enterprise.html；**about 页已下架，不要再跑 gen_about.py**）
- **部署**：`python deploy_ghpages.py`
- **留痕**：`git commit -m "feat: 入库 N 家企业 [来源] - 说明"`

**⑨ 上线后抽查** — 打开线上 enterprise.html，抽查本次入库企业（≥5 家）：卡片渲染正常、排序合理、中文介绍正常、评分徽章有值。发现问题自己直接修（不改核心逻辑），修完重部署；搞不定才汇报小爽。

### 3.2 入口 B：存量更新 / 修复（轻量分支）

从主流程第 ③ 步起，但**不做准入 / 去重**（企业已在库）。流程：
1. **定位**：明确改哪些企业、哪些字段、为什么改
2. **改数据**：直接编辑 `all_enterprises.json`（改前 `git commit` 当快照）
3. **跑门禁**：改了 recommend → 跑 `check_single.py`
4. **派走查子智能体**（改动 ≥ 10 家时）：同 §3.1 关卡 2
5. **自己审**：抽查改动过的企业
6. **重新生成 + 部署**：`gen_enterprise.py` → `deploy_ghpages.py`
7. **线上抽查** + **汇报小爽**（做了什么 / 改了什么 / 遗留什么）

> **与入口 A 的关键区别**：存量轻量改动**不需要小爽逐条预览确认**（除非小爽明确要求）；但部署前三道校验（门禁 / 走查 / 抽查）不能省。

### 3.3 入口 C：月度自动化（触发机制）

- 自动化 `automation-1784779809249`：每月 1 日 **23:00** 启动。
- 它做的事：读手册 → 扫当月资讯 → 提取库外新企业 → 走主流程第 ①–⑦ 步 → **生成预览表发小爽待审**（不自动合并部署）。
- 小爽确认后，由执行者走第 ⑧⑨ 步完成入库。

| 商业 | `deep_article_links` | 你 | 深度文章链接（0~2 条，有值才显） |
| 商业 | `news_coverage` / `related_news_ids` | 脚本自动 | 新闻关联 |
| 标签 | `tag_l2` | **你（从词表选 1~3）** | 二级标签，**写入权在你** |
| 标签 | `tag_l1` | 你（由 tag_l2 推导） | 一级标签 = `_l2_l1.json` 里该二级对应的 value |
| 标签 | `tags` / `category_l1` / `category_l2` / `business_tags` / `business_model` | 只读 / 废弃 | 旧体系，不动不删 |
| 评分 | `signal_strength` | 评分流水线 | 0~10（融资+IPO+时效），已有企业绝不重算 |
| 评分 | `info_score` / `diff_score` / `copy_score` | 评分流水线 | 0~10 三维 |
| 评分 | `total_score` | 评分流水线 | 综合分，前端展示主评分（见 §4.4） |
| 评分 | `research_value` / `value_score` | 旧 | fallback，新企业不算 |
| 元数据 | `source` / `update_time` / `ingest_time` | 你 | 来源 / 更新时间 / **首次入库时间（新企业必填）** |
| 元数据 | `silver_verdict` / `silver_reason` | 你 | 银发信号判定结果（核心 / 边缘 / 非银发） |
| 元数据 | `needs_review` / `flag` / `_legacy_rec` / `curated` / `competitors` | 脚本/历史 | 标记类，competitors 全空 |

**新入库最低必填**：serial, name, region, description(≥20字), source, ingest_time, update_time, silver_verdict。其余尽力，补不到标"待补充"。

### 4.2 打标签规则（执行权在你）

- **从现有词表选，不新造词**：词表 = `data/enterprise/_l2_l1.json`（key 是所有合法二级标签）。
- 每家企业选 **1~3 个二级标签**写入 `tag_l2`。
- `tag_l1` **不用手填**：由 `tag_l2` 经 `_l2_l1.json` 映射自动推导（一个二级只属一个一级）。
- 词表颗粒度有问题（如某个词太泛 / 该合并）→ **提建议给小爽**（流程 §7.3 复盘项），不要自己改词表定义。
- 不确定归哪个 → 先不填或选最宽的，标记 `needs_review`，交小爽定。

### 4.3 评分规则（四阶段，仅阶段 3/4 属评分）

> 阶段 1/2 是入库准入（§2），不在这里。

| 阶段 | 做什么 | 谁做 | 状态 |
|---|---|---|---|
| 阶段 3 信号强度 | 算 signal_strength 0~10（融资+IPO+时效） | 评分流水线脚本 | ✅ |
| 阶段 4 强模精评 | 算 info/diff/copy 三维 + 写 recommend | 强模型（HY3 至 8/5；后 DeepSeek V4 Flash） | ✅ 流水线化 |

**实现位置（代码事实，已核对 2026-07-23）**：
- 企业评分由 `scores_draft/rework/` 批量流水线产出：`batches_score/` 放 AI 评分批次 → `merge_batch_scores.py` 合并回真相源（**只写评分相关键，保留已有 signal_strength/research_value**）。
- `selection/signal_strength.py` 是**资讯**评分脚本（`compute_signal_strength(article, ...)`），**不是企业评分器**——V3 误归，已纠正。
- total_score 公式（来自 `merge_batch_scores.py` 与评分推荐规则）：`total_score = signal_strength + (info×0.3 + diff×0.3 + copy×0.2 + 综合×0.2)`，综合 = (info+diff+copy)/3。

**银发信号强度公式（阶段 3，供流水线 / 手填参考）**：各项相加，封顶 10，保底 0.5。

| 因素 | 规则 |
|---|---|
| 信源起点 | T1=0.5, T2=0.3, T3=0.1 |
| IPO | +6 |
| 融资（海外美元） | 10亿=5, 1亿=4, 5000万=3, 1000万=2, 500万=1, 100万=0.5 |
| 融资（国内元） | 10亿=6, 1亿=5, 5000万=4, 1000万=3, 500万=2, 100万=1, 50万=0.5 |
| 收购 | 100亿=6, 50亿=5, 10亿=4, 1亿=3, 5000万=2, 1000万=1 |
| 时效（每月重算） | 近1周=2.5, 近1月=2, 近2月=1.5, 近半年=1, 近1年=0.5, 更久=0.25 |

**铁律**：已有企业的 signal_strength / 历史评分**绝不重算**（保留原值）。只有新入库企业才计算。

### 4.4 门禁规则（部署前必过，针对 recommend）

**真实门禁 = `scores_draft/rework/check_single.py`**（R1–R10，已核对代码 2026-07-23）。

| 规则 | 检查内容（真实） | 不通过后果 |
|---|---|---|
| R1 | recommend 必须是单字符串（非 dict） | 补写 |
| R2 | **字数 50–240**（扫读舒适；V3 写的"≥15字"是错的） | 重写 |
| R3 | 不能是模板套话（BANNED 词表 + 正则，如"致力于为老年人""放到国内XX版图"） | 重写 |

### 4.5 前端展示 / 筛选 / 搜索 / 排序规则

**代码位置**：`gen_enterprise.py` 的 `build_card()`（约 197–602）、`filterEnt()`（筛选/搜索）、`sortEnt()`（排序）、`full_search`（搜索索引）。

**展示字段（有值才渲染，空值 / "未搜到/未披露/未知" 一律隐藏）**：
- `name`（固定用 name，不用 name_cn；name_cn 仅用于新闻匹配）
- `tag_l2`（头部标签栏，只展二级）
- `total_score`（头部徽章，0~100 制：`min(int(round(float(ts)*10)),100)` 封顶 100，色阶；research_value 不直接显示仅排序 fallback；signal_strength 仅 hover tooltip）

**排序（默认动态模式）**：

## §7 文档维护机制（含铁律与新原则）

### 7.1 什么时候更新本文档

| 触发条件 | 动作 |
|---|---|
| 规则变了（小爽确认的新规则） | 升版本号（V4→V5），旧版保留 |

| 新增 / 废弃字段 | 更新 §4.1 字典 |
| 流程增减步骤 | 更新 §3 |
| 每次任务结束后 | 按 §7.3 收尾清单检查是否要更新 |

### 7.2 版本规则

- 文件名 `企业库运营手册_V{N}.md`，N 递增；旧版不删，归档 `_archive_企业库旧文档/`。
- `企业库运维/` 目录永远只有**最新版** + `企业库任务规划_V*.md`。
- MEMORY.md 记录"当前最新版本号"。

### 7.3 任务收尾五步清单（每次任务结束必做）

1. **更新任务规划**（`企业库任务规划_V*.md`）：完成移"已完成"、新增登"进行中"、遗留登"待办"。
2. **检查手册版本**：本轮有规则变化？有 → 升版本号。
3. **写 memory**：`.workbuddy/memory/YYYY-MM-DD.md` 记本轮做了什么。
4. **git 提交留痕**：所有改动 commit（不一定要 push）。
5. **汇报小爽**：做了什么 / 改了什么规则 / 部署了什么 / 遗留什么。
6. **【复盘检查项·2026-07-23 新增】**：①文档与代码是否核对过、有无要修正（§0 铁律）；②打标签时发现词表颗粒度问题 → 提建议给小爽；③遗留的存量问题（英文/模板/信息不足）进度同步。

### 7.4 文档版本校验（每次写完文档必做，2026-07-23 新增）

**写完 / 改完本文档后，必须和上个版本逐节比对**，确保没漏重要信息：
- 上版有的章节 / 规则 / 代码位置，本版是否保留或显式说明"为何移除"
- 本版新增的原则 / 修正，是否在正文和变更说明里都体现
- 字段字典、门禁规则、前端规则这类"易漏清单"逐项核对
校验发现遗漏 → 补回，再提交。

### 7.5 归档清理（月度）

每月初（月度任务后）：检查 `_deprecated/` 下 1 个月前、确定不用的临时文件 → 删或续归档；根目录散落临时脚本移 `_deprecated/`（命名加 `企业库_` 前缀）。
