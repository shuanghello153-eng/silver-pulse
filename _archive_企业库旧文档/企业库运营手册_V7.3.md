## 1. 网站定位

Silver Pulse（银脉）= 银发经济投融资资讯聚合 **+ 企业数据库**，本质是小爽的**"选题情报台"**——让小爽早上打开网站，一眼看到"今天哪些企业 / 资讯值得写深度稿"。未来可能对外开放。

> 它不是资讯汇编站，是给小爽自己用的**选题决策工具**。每家企业 / 每条资讯的终点问题都是：中国银发经济创业者能从中借鉴什么？

## 4. 整体工作流程

### 4.1 概括介绍

所有任务走**同一套流程**，只是"从哪进、走到哪停"不同。不存在三套独立流程，不要抄三遍。

### 4.2 需求来源与分支

主要需求来源有三类（**注意：这不是穷尽规则，任何临时小需求——比如 UI/UX 微调——都可以走轻量分支，不必写死**）：

| 来源 | 走哪条流程 | 说明 |
|---|---|---|
| **A. 小爽给企业名单** | → 新企业入库（完整 1→10 步） | 最常见 |
| **B. 每月资讯扫描发现** | → 并入 A（新企业入库完整步） | 每月1日23:00扫描发现的新企业走完整入库流程，HY3免费期至 2026-08-05；之后强模改用 DeepSeek V4 Flash |
| **C. 存量走查发现问题** | → 从**步骤 3（补全字段）**起跳，跳过步骤 1–2（准入/去重已做过） | 例：英文 description 待译、模板话术待清、漏打标 |
| **D. 外部 AI 交接** | → 信源扩充 AI / 其他 AI 交来企业候选名单 | 见 §4.5 交接协议 |

- **轻量分支**：纯 UI/UX 小改动（搜索框跳动、placeholder 文案等）可走"前端校验→直接部署→事后补审"，不必走完整审核关卡（见 5.9）。

### 4.3 详细步骤（一条主流程，编号 1–10）

> 来源 C 从步骤 3 起；轻量 UI 改动可只走步骤 6→9 并事后补审，跳过8。

1. **银发相关性判断（入库准入）** —— 无信号直接删，不进库
2. **全库去重** —— 对 `all_enterprises.json` 全量比对
3. **补全所有字段** —— 联网/翻译补齐，重点：description / 标签 / 评分键 / 商业字段
4. **写推荐理由（recommend）** —— 强模产出
5. **算评分** —— 信号强度（脚本）＋ 四维精评
6. **前端展示校验** —— 跑生成器，肉眼看卡片渲染
7. **质量门禁自测** —— 跑门禁脚本 + 子智能体走查
8. **小爽审核** —— 发全字段预览表，硬卡点
9. **合并部署** —— 编辑真相源 → 生成 → 部署 gh-pages
10. **上线走查 + 抽查** —— 派子智能体走查，问题回滚

### 4.4 ⚡️ 流程衔接说明（V7.3 重写）

#### 4.4.1 各环节衔接方式总览

整体流程是**「文档编排 + 代码工具」混合模式**。各环节衔接方式：

| 步骤 | 衔接方式 | 自动化程度 | 说明 |
|---|---|---|---|
| **步骤 1a 初筛** | ⚡️ **可调用脚本** (`config.SILVER_STRONG_KEYWORDS`) | 半自动 | 强词命中即通过初筛；脚本存在但**未自动接入入库流水线**，当前靠 AI 手动判断 |
| **步骤 1b 二筛** | AI 读手册执行 | 人工 | 低模做银发相关性是非题判断 |
| **步骤 2 去重** | AI + ⚡️ 脚本辅助 | 半自动 | 关键词提取匹配可脚本化；增量比对需 AI |
| **步骤 3 补全字段** | AI 联网/翻译 | 半自动 | 缺值标"待补充"；部分字段可代码填充 |
| **步骤 4 推荐理由** | AI 强模产出 | 人工 | 纯 AI 写作，无脚本 |
| **步骤 5 评分** | ⚡️ **全自动代码** | **全自动** | `selection/signal_strength.py`(信号) + `merge_batch_scores.py`(四维合并)，确定性的 |
| **步骤 6 前端生成** | ⚡️ **全自动代码** | **全自动** | `gen_enterprise.py` 一键生成 |
| **步骤 7 质量门禁** | ⚡️ **代码**(机械) + 子智能体(语义) | 半自动 | D1-D4/R1-R10 脚本跑；语义走查派子智能体 |
| **步骤 8 小爽审核** | 人工卡点 | 人工 | 不自动跳过 |
| **步骤 9 部署** | ⚡️ **代码** | **全自动** | `deploy_ghpages.py`（需批准才执行） |
| **步骤 10 走查** | 子智能体 + 人眼 | 人工 | 语义判断 |

#### 4.4.2 为什么不做全脚本化串联

步骤 1b/2(增量)/4/8 包含语义判断（银发相关性、去重冲突裁决、推荐理由写作、发布放行），**强制脚本化会降质量**。月度自动化（每月1日23:00）已把步骤 1→7 串成自动触发，但**停在步骤8不自动部署**——这是合理的半自动衔接。

#### 4.4.3 流程不会卡住的保障

**原则：每个步骤都有明确的"输入→输出→下一步"定义。如果某步卡住：**
- **脚本报错** → 检查输入数据格式，看报错信息修数据，重跑
- **AI 判断拿不准** → 标记"待小爽定"，进入步骤 8 让小爽拍板，**不阻塞后续其他企业**
- **子智能体超时/质量差** → 换一种方式表达 prompt，或自己先做一遍再让它复查
- **小爽驳回** → 见步骤 8 的驳回流程（§5.8），有明确回退路径

**关键设计：单家企业不阻塞批量。** 如果一批 20 家中有 3 家有争议，先把 17 家推到下一步，3 家标记"待定"单独处理。

#### 4.4.4 后续衔接约定

每个步骤的"接棒"靠本手册的编号步骤驱动；确定性操作（评分类、生成类、门禁类、部署类）直接调对应脚本；语义操作（判断/写作/审核）由 AI/小爽人脑完成。新人/新 AI 看 §4.3 编号即可知道"现在该干嘛、调什么脚本"。

### 4.5 ⚡️ 外部 AI 交接协议（新增）

当**信源扩充 AI**（或其他 AI）交来一批企业候选时：

```
接收方（你）的动作：
1. 接收结构化文件（JSON/Excel），放入 handoff/enterprise_inbox/
2. 从步骤 1 开始走完整入库流程（不跳步）
3. 完成后产出结果放 handoff/enterprise_outbox/
4. 如果需要反馈权源扩充 AI（比如某家其实不该入库），写一份简短说明放回 inbox
```

**为什么不定死"必须通过某个目录交接"**：因为 AI 可能换、上下文可能断。核心原则是**"拿到候选→按手册走流程→产出结果"**，不依赖特定 AI 的在线状态。交接文件是异步的、持久的（文件系统比对话窗口可靠）。

### 5.2 ⚡️ 步骤 2 · 全库去重（增强版）

**比对对象必须是全库 `all_enterprises.json`**

#### 2.1 ⚡️ 脚本辅助：关键词粗筛（新增思路）

在精确匹配前，先用脚本做一轮**关键词提取+模糊匹配**：

```python
# 思路（可写成 check_dedup_keyword.py）：
# 1. 提取企业核心名称：去掉 "公司"/"有限公司"/"股份有限公司"/"集团"/"Inc."/"Corp." 等后缀
#    再去掉已知城市名前缀（如 "北京"/"上海"/"Tokyo"/"New York" 等）
# 2. 用核心词在全库 name/name_cn 中做子串匹配
# 3. 命中的列为"疑似重复候选"
# 4. 候选再交给 AI 做信息增量比对
```

**这个脚本的收益**：大批量入库时（比如月度扫描发现 30 家），先用脚本排除掉"明显不重复的"，减少 AI 比对工作量。

#### 2.2 精确匹配（原有逻辑不变）

精确匹配 `name` / `name_cn` 完全一致 → 已存在；模糊相似度 → 疑似重复需确认。

三种结果处理：

| 情形 | 处理 |
|---|---|
| **一致**（信息无差异） | 跳过，不新建 |
| **增量**（相似但信息有补充） | 合并进已有记录，补增量字段；拿不准标"待小爽定" |
| **冲突**（疑似同家但关键业务矛盾） | 联网复核，以证据为准订正；交小爽裁决 |

> ⚡️ **低成本改进点**：步骤 2.1 的关键词粗筛脚本一旦建好，每次入库可自动跑，**省掉 AI 对"明显不重复"企业的比对时间**。

### 5.3 ⚡️ 步骤 3 · 补全所有字段

联网 / 翻译补齐字段字典（附录 6.1）里所有在使用的字段，尽量都补齐。

- **必填最低门槛**：`serial` / `name` / `region` / `description(≥20字)` / `source` / `ingest_time` / `update_time`。
- **补不到** → 标 **"待补充"**，**禁止编造**（错数据毁掉整篇公信力）。
- **`serial`**：格式 `#XXXX`，取现有最大值 +1。
- **重点字段**：
  - **description（企业介绍）**：中文、≥20 字、说清三件事——**做什么、服务谁、怎么赚钱**（信息不足至少前两件）；禁模板套话、禁英文主导、禁夹带原始标记（如【提供资源】）；单位用中文（万/亿）。
  - **标签 `tag_l1/tag_l2`**：从 `_l2_l1.json` 现有体系选 1~3，不自造新词，若均不符合，可向小爽提建议。⚡️ **打标签时顺便校验 tag_l2 是否在 `_l2_l1.json` 词表中**，不在即报警（不要等走查才发现）。
  - **评分键 / `funding_*` / 动态时间**：一并补齐。
  - **投融资：商业字段非常重要，但不一定有。**

- **⚡️ 搜索索引修正（V7.3 修正）**：前端搜索索引 = **`name`（含中英文 name_cn）+ `description` + `tags`（含 tag_l1 / tag_l2 / _l2_l1.json 中的同类词 synonyms）+ `stage` + `recommend`**。⚡️ 之前漏了 name_cn 和同类词扩充，已修正。

### 5.4 步骤 4 + 5 · 评分与推荐理由

**评分架构（阶段 1–2 为"银发相关性判断 / 准入"，见 5.1；阶段 3–4 为本步骤的评分）：**

- **⚡️ 阶段 3 · 信号强度（脚本 `selection/signal_strength.py`，0~10，封顶 10 保底 0.5）**，企业与资讯共用同一函数 `compute_signal_strength()`，按事件分级换算：
  - 信源起点：T1=0.5，T2=0.3，T3=0.1
  - IPO = +6；融资（海外美元）：≥10亿=5 / 1亿=4 / 5000万=3 / 1000万=2 / 500万=1 / 100万=0.5
  - 融资（国内元）：≥10亿=6 / 1亿=5 / 5000万=4 / 1000万=3 / 500万=2 / 100万=1 / 50万=0.5
  - 收购（海内外）：≥100亿=6 / 50亿=5 / 10亿=4 / 1亿=3 / 5000万=2 / 1000万=1
  - 时效：近1周=2.5 / 近1月=2 / 近2月=1.5 / 近半年=1 / 近1年=0.5 / 更久=0.25

- **⚡️ 阶段 4 · 强模四维精评**：输出 `recommend` + 四维评分

**⚡️ 四维评分公式（total_score，小爽 2026-07-24 确认，代码 `merge_batch_scores.py:66-72` 实现）：**
```
total_score = 信号强度 × 30% + 信息量 × 30% + 差异化 × 20% + 可复制 × 20%
```

**⚡️ 评分范围铁律（V7.3 明确写入，代码已同步实现防御性封顶）：**
- 每个维度（信号/信息/差异/复制）：**0 ~ 10 分**，超过 10 分取 10 分
- total_score：**0 ~ 10 分**（四维加权求和后封顶 10）
- **内部存储和计算全部用 0~10 分制**
- **前端展示时统一 × 10** → 显示值范围 0~100（见 `gen_enterprise.py:357`）
- 这样评分者从 0~10 打分更直观，不用从 0~100 里硬凑

**推荐理由（recommend）写法：**
- 用一段自然流畅的话，把**信息量 / 差异化 / 可复制**三方面判断融进去讲（信号强度已在列表展示为评分徽章，推荐理由里不复述），不刻意分段、不逐维列分。
- 写完后自检：**卡片/列表已展示的结构化信息**（融资金额、轮次、标题、摘要、来源、日期等）推荐理由里**不再重复陈述**。
- 不写"死规则"式套话；要有洞察（为什么这家值得写）。
- ⚡️ 与 description 明确分工：description 讲"它是谁、做什么"（基本事实），recommend 讲"为什么值得写"（判断洞察）。**基本事实放 description，判断放 recommend，两者不重复。** 写推荐理由前就要区分清楚，避免返工。
- ⚡️ **禁止机械式地写"信息量：xxx；差异化：xxx；可复制：xxx"这种三段式**——要融成自然的一段话，让读者（小爽）读起来像在看一个编辑的真判断，而不是在填表格。

### 5.6 ⚡️ 步骤 7 · 校验（三道关卡 + 走查循环）

#### 关卡 1：门禁自测（⚡️ 脚本一次跑完 D1-D4 + R1-R10）

**⚡️ Description 质量（门禁 D1–D4）**
1. 中文（品牌名、产品名等专有名词可保留英文）；
2. ≥20 字；
3. 禁止通用模板句（一句话能套在任何企业身上的，如"公司通过多渠道拓展市场"就是废话）；
4. 禁止夹带原始数据标记（如【提供资源】【需求数源】这类来源表格残留）；
5. 查不到的信息写"待补充"，**禁止编造**。

**⚡️ Description 门禁规则（D1-D4，计划建 `check_description.py`，复用 check_single.py 的 BANNED 词表）**

| 编号 | 检查内容 | 实现方式 | 不通过后果 |
|---|---|---|---|
| D1 | description 非空且 ≥20 字 | `len(description.strip()) >= 20` | 拦截 |
| D2 | 非纯英文 | 中文字符数 > 总长度×30% | 拦截 |
| D3 | 命中 BANNED 模板句 | 复用 `check_single.py` 的 `BANNED` 列表 + `BANNED_RE` 正则 | 拦截 |
| D4 | 无原始标记残留 | 检测【提供资源】【需求数源】等标记 | 拦截 |

**Recommend 门禁规则（R1-R10，唯一正式门禁 `check_single.py`）**

| 编号 | 检查内容 | ⚡️ 怎么校验的？实现原理 | 不通过后果 |
|---|---|---|---|
| R1 | 单字符串（非列表/非 null） | `isinstance(recommend, str)` 类型检查 | 拦截 |
| ⚡️ R2 | **字数 20–200** | `content_len(recommend)` 计算去空格后的字符数，<20 或 >200 即拦截 | 拦截 |
| R3 | 禁模板套话 | 遍历 `BANNED` 列表（60+ 条固定句）做子串匹配 + `BANNED_RE` 正则（15 条结构级模式）| 命中即毙 |
| R4（别名 R-name）| 禁直接出现企业名 | 检查 `name` 和 `name_cn` 是否作为子串出现在 recommend 中 | 拦截 |
| ⚡️ **R5** | **须覆盖三维度：信息量 / 差异化 / 可复制** | **用三个关键词列表（DIM_INFO/DIM_DIFF/COPY 各 15~20 个近义词）检测 recommend 是否包含至少一个来自每组的词**。例如 DIM_INFO 包含["信息","资料","年报","素材","可挖","详实"] 等；DIM_DIFF 包含["差异","独特","壁垒","少见"] 等；DIM_COPY 包含["可复制","借鉴","国内","对标"] 等。**不要求出现"信息量/差异化/可复制"这三个确切词本身**——而是看语义覆盖。 | 缺任一维度即拦截 |
| R-redundancy | 禁复述列表已有字段 | (a) 融资数字：抽取 recommend 中 ≥2 位数字串，与 funding 字段的数字取交集；(b) 阶段状态词：STATUS_WORDS 与 stage 字段交叉；(c) description/highlights 4-gram Jaccard >0.65 | 拦截 |
| ⚡️ **R-integrity** | **前后半段讲同一赛道（防拼接错误）** | **将 recommend 按字符数对半切，前后半段分别匹配 27 个赛道关键词（殡葬/康复/养老/保险...）。如果前半段命中的赛道词集合 与 后半段命中的赛道词集合 交集为空 → 说明前后讲的不是同一个赛道 → 大概率是拼接错误**。仅当 recommend ≥50 字时启用（太短的文本切分无意义）。 | 拦截 |
| R-noabs | 禁绝对化用词 | 遍历 ABSOLUTE 列表（20 条如"国内空白/市场空白/独家垄断"）| 拦截 |
| R-jargon | 禁技术黑话 | 遍历 JARGON 列表（16 条如"CNS/VBC/DRG/SaaS化"）| 拦截 |
| R-filler | 禁废话填充 | 遍历 FILLER 列表（8 条如"赋能/一站式/闭环生态"）| 拦截 |
| ⚡️ **R10** | **跨企业雷同度 >0.5** | **对每两家企业的 recommend 做：(a) 最长公共子串(LCS)长度 ≥15 且 (b) 字符集 Jaccard 相似度 >0.5 → 判定为雷同**。LCS 用动态规划算法（O(n×m)），超过 400 万字符时截断到前 2000 字防超时。**复杂度 O(n²)，企业批量大时略慢但可接受（1460 家全量两两对比约 1~2 秒）**。 | 拦截 |

> **R5 的局限性**：关键词匹配法可以被"凑词"绕过（比如随便塞一个"信息"字但不真有信息量判断）。所以 R5 是**必要不充分条件**——过了 R5 只说明"至少提到了三个维度"，真正有质量的判断要靠关卡 2 子智能体语义走查。
>
> **R-integrity 的设计意图**：防止 AI 在生成 recommend 时把两家企业的评语拼在一起（前半是 A 家的判断、后半是 B 家的）。27 个赛道词覆盖了银发经济的主要方向，如果前后半段赛道词不重叠，大概率是拼接错了。
>
> **R10 的性能**：全量 1460 家两两对比约 106 万对，但 LCS 有 15 的最小长度门槛 + 先做字符集预筛（Jaccard 快速淘汰大部分），实际运行约 1~3 秒，可接受。

**⚡️ 规则只在一处（门禁）写明**：推荐理由字数等硬性规则以 `check_single.py` 的 R1–R10 为唯一权威，关卡2 prompt 不再重复写字数阈值，避免两处不一致时改丢冲突。description 与 recommend 的"质量怎么判"以本关卡规则为准，子智能体走查时仍按语义细查。

#### ⚡️ 关卡 2：派独立走查子智能体（循环机制）

派一个 general-purpose 子智能体，给它以下指令：

> 你是企业库质量走查员。
> 请检查这批新企业的数据质量，重点关注：
> 1. ⚡️ **description 与 recommend 一起查**：description 是否大部分为中文、是否说清三件事（做什么/服务谁/怎么赚钱）、是否模板套话、与 recommend 是否重复；recommend 是否满足门禁规则（不为空、非套话、不雷同、有真判断、不复述 description 基本事实）；
> 2. ⚡️ **recommend 三维度检查**：是否真的给出了信息量（素材够不够挖）、差异化（有什么独特之处）、可复制（国内能学什么）的有理有据判断？还是只在凑字？**不要看是否出现了"信息量/差异化/可复制"这几个词，而要看实质内容是否覆盖了这三个方面。**
> 3. 两者信息是否重复（recommend 不应复述 description 已有的基本事实）；
> 4. 银发信号判定是否合理（真的跟银发经济相关吗）
> 5. 字段是否齐全（尤其是 description / source / ingest_time）
> 6. 标签是否在 `_l2_l1.json` 词表中
>
> 输出一份问题清单（企业名 + 字段 + 问题 + 建议修改）。

**⚡️ 子智能体走查循环（V7.3 新增）：**

```
第一轮走查 → 主智能体（你）修复问题
    ↓
第二轮走查（另一个子智能体或同一个重新跑）
    ↓ 有问题 → 主智能体再修 → 最多两轮
    ↓ 通过 → 进入关卡 3
```

**规则**：
- 子智能体**最多走查 2 轮**（避免无限循环浪费积分）
- 每轮之间由**主智能体（你）**负责修改，不是让子智能体自己改
- 如果 2 轮后仍有问题，标记"待小爽定"，进入步骤 8 让小爽裁决
- **recommend 和 description 的走查合并在一次子智能体调用中完成**（不派两个分别查）

**子智能体反馈的问题，你自己先修。能修的自己修，不确定的标记出来。**

#### 关卡 3：自己审一遍

自己作为第二双眼睛再过一遍：
- 打开生成的预览表（CSV/Excel），逐行看
- 重点检查：刚才子智能体发现的问题是否修好了、有没有漏网的

- MEMORY.md 记录"当前最新版本号"。

#### ⚡️ 文档维护标准（沿用 V7.2）

1. **顶部更新栏**：每次发版在最顶部写「本次更新：日期 + ⚡️ 改动点列表」（格式见本版开头）。
2. **正文标记**：本次新增/修改的文字用 ⚡️ + **加粗**标记；下次发版时去掉上次的 ⚡️，只保留当次，避免干扰小爽审读。
3. **全量核对**：写完后与上一版逐节比对，确保没漏重要信息（见 §6.4 版本沿革）。
4. **改动点汇报**：任何改动点都要主动告诉小爽（哪怕只是删冗余），小爽只查 ⚡️ 处，未标记即默认未改。
5. **规则单一来源**：硬性规则（如门禁字数）只在门禁节写一处，其他节引用不重复写，防改丢冲突。

#### ⚡️ 文档↔代码双向一致性机制（V7.3 核心）

**原则：不以"代码为准"一刀切。代码也可能错（比如这次排序键用了旧 research_value 就是 bug），文档也可能落后。**

**标准动作（每次改规则时必做）：**

```
┌─────────────────────────────────────────────────────┐
│                 改代码之前                            │
│  1. 读手册对应章节，确认文档写的规则是什么              │
│  2. 如果代码与文档不一致 → 判断哪个是对的             │
│     - 代码是新改的、文档是旧的 → 改文档跟上代码        │
│     - 文档是小爽最新确认的、代码是旧的 → 改代码跟上文档 │
│     - 都不确定 → 问小爽                             │
│  3. 改完代码后，确认文档是否需要同步更新               │
│  4. 同一次 commit 包含代码改动 + 文档改动（如有）      │
├─────────────────────────────────────────────────────┤
│                 改文档之前                            │
│  1. 读对应代码，确认代码实现的是什么                  │
│  2. 如果文档与代码不一致 → 同上判断流程                │
│  3. 改完文档后，确认代码是否需要同步修改               │
│  4. 同上，同 commit                                 │
└─────────────────────────────────────────────────────┘
```

**具体执行要点**：
- **改评分公式/门禁值** → 必须代码+文档一起改，同一次 commit
- **改前端展示字段** → 检查文档 §5.5 字段表是否需要更新
- **改排序逻辑** → 检查文档 §5.5 排序说明是否需要更新
- **发现不一致但本轮不改** → 在收尾清单登记，标注"待处理：文档代码不一致[位置]"

### 6.5 历史教训（写进流程）

1. 改文档不能把已定对的结论又改丢（每次新建议是叠加，不是覆盖）。
2. 清任务清单前必须先核实并登记，不得批量误清（金额万/亿、阶段4评分早已落地，曾误当摆设清掉）。
3. ⚡️ 文档与代码可能不一致——**任务前必须核对代码，发现文档错要改文档，发现代码错也要改代码**（本次排序键 bug 就是证明）。
4. 所有规则尽量融入流程带触发条件，不单独存放成死内容。
5. 写完文档跟上版校验，防漏信息。
6. ⚡️ 评分公式/门禁等"硬规则"一旦变更，必须**代码与文档同步改、同一次 commit**，避免两处漂移。
7. ⚡️ **不要盲目相信"代码为准"——代码也可能是旧的/错的（如 research_value 排序键）。要以"经过判断的最新正确版本"为准。**

以下是可以**用脚本/固定流程替代 AI 调用**的措施，目的是**降低积分消耗、提高稳定性、减少模型调用**：

| 序号 | 改进项 | 方式 | 节省什么 | 优先级 |
|---|---|---|---|---|
| 1 | **步骤 1 初筛自动化** | 把 `SILVER_STRONG_KEYWORDS` 命中检测写成一行函数，入库时先跑函数过滤掉明显无信号的 | 省掉 AI 对"明显不相关企业"的判断时间 | 高（每次入库都触发） |
| 2 | **步骤 2 去重关键词提取脚本** | 建 `check_dedup_keyword.py`：去公司后缀→提取核心词→全库子串匹配 | 省掉 AI 对"名字完全不同"企业的比对时间 | 中（批量入库时效果明显） |

| 4 | **标签词表自动校验** | 打 tag_l2 时自动比对 `_l2_l1.json`，不在词表里的报警 | 省走查时才发现标签错误的返工 | 中 |

## ⚡️ 附 B：自动化串接考量（V7.3 新增，供讨论）

### 问题：要不要把步骤 1→7 串成一个全自动脚本？

**我的判断：不建议现在做全串接，但可以做局部串接。**

#### 利（串接的好处）
- 月度任务触发后无需人工干预跑到步骤 7
- 减少人为遗忘（比如忘了跑门禁）
- 适合"大批量低风险"企业（如月度扫描发现的明显合规企业）

#### 弊（串接的风险）
- **步骤 1b（二筛）和步骤 4（推荐理由）本质是语义判断**，强行脚本化会降质量
- 步骤 2 的去重冲突裁决需要人脑
- 出问题时难以定位是哪一步出了问题
- **一旦流程固化，改进流程本身的成本变高**

#### 我的建议：分阶段走

```
第一阶段（现在就能做）：
  步骤 5（评分）+ 步骤 6（生成）+ 步骤 7 关卡 1（门禁脚本）
  → 这三步全是确定性的，串起来零风险
  → 月度自动化已经做到步骤 7 门禁脚本，很合理

第二阶段（未来考虑）：
  步骤 1a（初筛）+ 步骤 2a（关键词粗筛）
  → 也是确定性的，可以串
  → 但要先建对应的脚本（目前还没有）

第三阶段（暂不做）：
  步骤 1b / 4 / 7关卡的语义部分
  → 这些需要真正理解上下文，不适合强行自动化
  → 除非模型能力大幅提升+成本大幅下降
```

**底线：步骤 8（小爽审核）永远不能自动化。** 这是最后的质量守门人。
