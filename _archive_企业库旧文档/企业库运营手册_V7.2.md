## 1. 网站定位

Silver Pulse（银脉）= 银发经济投融资资讯聚合 **+ 企业数据库**，本质是小爽的**"选题情报台"**——让小爽早上打开网站，一眼看到"今天哪些企业 / 资讯值得写深度稿"。未来可能对外开放。

> 它不是资讯汇编站，是给小爽自己用的**选题决策工具**。每家企业 / 每条资讯的终点问题都是：中国银发经济创业者能从中借鉴什么？

- **采集（信源与资讯）**：由**信源扩充 AI** 负责（RSS-first，44 信源，海外为主）。企业库不碰采集。

## 4. 整体工作流程

### 4.1 概括介绍

所有任务走**同一套流程**，只是"从哪进、走到哪停"不同。不存在三套独立流程，不要抄三遍。

### 4.2 需求来源与分支

主要需求来源有三类（**注意：这不是穷尽规则，任何临时小需求——比如 UI/UX 微调——都可以走轻量分支，不必写死**）：

| 来源 | 走哪条流程 | 说明 |
|---|---|---|
| **A. 小爽给企业名单** | → 新企业入库（完整 1→10 步） | 最常见 |
| **B. 每月资讯扫描发现** | → 并入 A（新企业入库完整步） | 每月1日23:00扫描发现的新企业走完整入库流程，HY3免费期至 2026-08-05；之后强模改用 DeepSeek V4 Flash | 
| **C. 存量走查发现问题** | → 从**步骤 3（补全字段）**起跳，跳过步骤 1–2（准入/去重已做过） | 例：英文 description 待译、模板话术待清、漏打标 |

- **轻量分支**：纯 UI/UX 小改动（搜索框跳动、placeholder 文案等）可走"前端校验→直接部署→事后补审"，不必走完整审核关卡（见 5.9）。

### 4.3 详细步骤（一条主流程，编号 1–10）

> 来源 C 从步骤 3 起；轻量 UI 改动可只走步骤 6→9 并事后补审，跳过8。

1. **银发相关性判断（入库准入）** —— 无信号直接删，不进库
2. **全库去重** —— 对 `all_enterprises.json` 全量比对
3. **补全所有字段** —— 联网/翻译补齐，重点：description / 标签 / 评分键 / 商业字段
4. **写推荐理由（recommend）** —— 强模产出
5. **算评分** —— 信号强度（脚本）＋ 四维精评
6. **前端展示校验** —— 跑生成器，肉眼看卡片渲染
7. **质量门禁自测** —— 跑 `check_single.py`
8. **小爽审核** —— 发全字段预览表，硬卡点
9. **合并部署** —— 编辑真相源 → 生成 → 部署 gh-pages
10. **上线走查 + 抽查** —— 派子智能体走查，问题回滚

### 4.4 流程衔接说明（⚡️ 新增）

整体流程是**「文档编排 + 代码工具」混合模式**，不是全自动化大脚本。各环节衔接方式如下：

| 步骤 | 衔接方式 | 说明 |
|---|---|---|
| 步骤1 银发相关性判断 | AI 读手册执行 | 强词脚本可调但**未自动接入入库流程**，当前靠 AI 判断 |
| 步骤2 全库去重 | AI 手动比对 | 无全自动脚本（去重需语义判断） |
| 步骤3 补全字段 | AI 联网/翻译 | 半自动，缺值标"待补充" |
| 步骤4 推荐理由 | AI 强模产出 | 纯 AI 写作，无脚本 |
| 步骤5 评分 | ⚡️ **代码**：`selection/signal_strength.py`（信号强度）+ `merge_batch_scores.py`（四维合并） | 确定性计算，脚本可重复跑 |
| 步骤6 前端生成 | ⚡️ **代码**：`gen_enterprise.py` | 一键生成，无交互 |
| 步骤7 质量门禁 | ⚡️ **代码**：`check_single.py`（机械）+ 子智能体（语义） | 机械部分脚本跑，语义部分派子智能体 |
| 步骤8 小爽审核 | 人工卡点 | 不自动跳过 |
| 步骤9 部署 | ⚡️ **代码**：`deploy_ghpages.py` | 一键部署（需小爽批准才执行） |
| 步骤10 走查 | 子智能体 + 人眼 | 语义判断 |

**为什么不做全脚本化串联**：步骤 1/2/4/8 包含语义判断（银发相关性、去重冲突、推荐理由写作、发布放行），脚本化会降质量。月度自动化（每月1日23:00）已把步骤 1→7 串成自动触发，但**停在步骤8不自动部署**——这是合理的半自动衔接。

**后续衔接约定**：每个步骤的"接棒"靠本手册的编号步骤驱动；确定性操作（评分类、生成类、门禁类、部署类）直接调对应脚本；语义操作（判断/写作/审核）由 AI/小爽人脑完成。新人/新 AI 看 §4.3 编号即可知道"现在该干嘛、调什么脚本"。

- **第二步 · 低模判断（便宜 AI 是非题）**：符合任一即保留——
  - 直接面向 **50 岁+或60岁+** 人群（C 端）；
  - 面向 **Medical/Medicare Advantage（美国联邦医保优势计划）参保老人（C 端）**
  - 为上述[服务 C端人群的 B 端企业]提供方提供产品 / 服务


**直接拒绝（不论是否命中强词）**：综合电商（养老仅"规划中"）、品牌 PR / 活动传播、Web3 / 通用 AI 平台、泛再生医学 / 高端医疗绿通、泛医疗 VC、泛融媒体。

> 关键词门禁是辅助，**最终以实质业务判断为准**；不确定可联网核查，默认从严（无信号即删）。

### 5.2 步骤 2 · 全库去重

**比对对象必须是全库 `all_enterprises.json`**

精确匹配 `name` / `name_cn` 完全一致 → 已存在；模糊相似度 → 疑似重复需确认。

三种结果处理：

| 情形 | 处理 |
|---|---|
| **一致**（信息无差异） | 跳过，不新建 |
| **增量**（相似但信息有补充） | 合并进已有记录，补增量字段；拿不准标"待小爽定" |
| **冲突**（疑似同家但关键业务矛盾） | 联网复核，以证据为准订正；交小爽裁决 |


### 5.3 步骤 3 · 补全所有字段

联网 / 翻译补齐字段字典（附录 6.1）里所有在使用的字段，尽量都补齐。

- **必填最低门槛**：`serial` / `name` / `region` / `description(≥20字)` / `source` / `ingest_time` / `update_time`。
- **补不到** → 标 **"待补充"**，**禁止编造**（错数据毁掉整篇公信力）。
- **`serial`**：格式 `#XXXX`，取现有最大值 +1。
- **重点字段**：
  - **description（企业介绍）**：中文、≥20 字、说清三件事——**做什么、服务谁、怎么赚钱**（信息不足至少前两件）；禁模板套话、禁英文主导、禁夹带原始标记（如【提供资源】）；单位用中文（万/亿）。
  - **标签 `tag_l1/tag_l2`**：从 `_l2_l1.json` 现有体系选 1~3，不自造新词，若均不符合，可向小爽提建议。
  - **评分键 / `funding_*` / 动态时间**：一并补齐。
  - **投融资：商业字段非常重要，但不一定有。

### 5.4 步骤 4 + 5 · 评分与推荐理由

**评分架构（阶段 1–2 为"银发相关性判断 / 准入"，见 5.1；阶段 3–4 为本步骤的评分）：**

- **⚡️ 阶段 3 · 信号强度（脚本 `selection/signal_strength.py`，0~10，封顶 10 保底 0.5）**，按事件分级换算：
  - 信源起点：T1=0.5，T2=0.3，T3=0.1
  - IPO = +6；融资（海外美元）：≥10亿=5 / 1亿=4 / 5000万=3 / 1000万=2 / 500万=1 / 100万=0.5
  - 融资（国内元）：≥10亿=6 / 1亿=5 / 5000万=4 / 1000万=3 / 500万=2 / 100万=1 / 50万=0.5
  - 收购（海内外）：≥100亿=6 / 50亿=5 / 10亿=4 / 1亿=3 / 5000万=2 / 1000万=1
  - 时效：近1周=2.5 / 近1月=2 / 近2月=1.5 / 近半年=1 / 近1年=0.5 / 更久=0.25

- **⚡️ 阶段 4 · 强模四维精评**：输出 `recommend` + 四维评分

**⚡️ 四维评分公式（综合评分 / total_score，小爽 2026-07-24 确认，代码 `merge_batch_scores.py` 实现）：**
```
综合评分 = 信号强度 × 30% + 信息量 × 30% + 差异化 × 20% + 可复制 × 20%
```
⚡️ **每维 0~10，四维直接加权求和（无"综合"元维度，信号强度也乘权重，不再直加）。** ⚡️ 前端显示时 `total_score × 10` 取整、封顶 100（见 §5.5）。

**推荐理由（recommend）写法：**
- 用一段自然流畅的话，把**信号强度 / 信息量 / 差异化 / 可复制**四方面判断融进去讲，不刻意分段、不逐维列分。
- 写完后自检：**卡片/列表已展示的结构化信息**（融资金额、轮次、标题、摘要、来源、日期等）推荐理由里**不再重复陈述**。
- 不写"死规则"式套话；要有洞察（为什么这家值得写）。
- ⚡️ 与 description 明确分工：description 讲"它是谁、做什么"（基本事实），recommend 讲"为什么值得写"（判断洞察）。**基本事实放 description，判断放 recommend，两者不重复。** 写推荐理由前就要区分清楚，避免返工。

### 5.6 步骤 7 · 校验（三道关卡）

#### 关卡 1：门禁自测

**⚡️ 介绍（description）质量标准（门禁脚本 D1–D4，详见下方说明）**
1. 中文（品牌名、产品名等专有名词可保留英文）；
2. ≥20 字；
3. 禁止通用模板句（一句话能套在任何企业身上的，如"公司通过多渠道拓展市场"就是废话）；
4. 禁止夹带原始数据标记（如【提供资源】【需求数源】这类来源表格残留）；
5. 查不到的信息写"待补充"，**禁止编造**。

**⚡️ Description 门禁脚本（新增 `check_description.py` 计划，当前可手验，D1–D4 规则）**
| 编号 | 检查内容 | 不通过后果 |
|---|---|---|
| D1 | description 非空且 ≥20 字 | 拦截 |
| D2 | 非纯英文（中文字符数 > 总长度×30%） | 拦截 |
| D3 | 命中 BANNED 模板句（复用 check_single.py 的 BANNED 列表+正则） | 拦截 |
| D4 | 无原始标记残留（【提供资源】【需求数源】等） | 拦截 |

**推荐理由（recommend）门禁**

部署前必跑 `scores_draft/rework/check_single.py`（**唯一正式门禁，针对 `recommend`**，代码见 §6.2）。

| 编号 | 检查内容 | 不通过后果 |
|---|---|---|
| R1 | 单字符串（非列表/非 null） | 拦截 |
| ⚡️ R2 | **字数 20–200** | 拦截 |
| R3 | 禁模板套话（如"渠道招商"类） | 拦截 |
| R4 | （别名 R-name）禁直接出现企业名 | 拦截 |
| R5 | 须覆盖**三维度**：信息量 / 差异化 / 可复制（不要求信号维度，融资/收购/上市已在列表展示，禁止复述） | 拦截 |
| R-redundancy | 禁复述列表已有字段（融资数字等） | 拦截 |
| R-integrity | 赛道判定与标签一致 | 拦截 |
| R-noabs | 禁绝对化用词（"最/第一/唯一"无依据） | 拦截 |
| R-jargon | 禁黑话（无必要术语） | 拦截 |
| R-filler | 禁废话填充 | 拦截 |
| R10 | 跨企业雷同度 >0.5 | 拦截 |

R1–R10 全过才进入下一关。不过的返回重新调整，直到通过。

> ⚡️ **规则只在一处（门禁）写明**：推荐理由字数等硬性规则以 `check_single.py` 的 R1–R10 为唯一权威，关卡2 prompt 不再重复写字数阈值，避免两处不一致时改丢冲突。description 与 recommend 的"质量怎么判"以本关卡规则为准，子智能体走查时仍按语义细查。

#### 版本规则

- 文件名 `企业库运营手册_V{N}.md`，N 递增；旧版不删，归档 `_archive_企业库旧文档/`。
- `企业库运维/` 目录永远只有**最新版** + `企业库任务规划_V*.md` + `企业库行为准则.md`（独立文档）。
- MEMORY.md 记录"当前最新版本号"。

#### ⚡️ 文档维护标准（小爽 2026-07-24 确认写入）

1. **顶部更新栏**：每次发版在最顶部写「本次更新：日期 + ⚡️ 改动点列表」（格式见本版开头）。
2. **正文标记**：本次新增/修改的文字用 ⚡️ + **加粗**标记；下次发版时去掉上次的 ⚡️，只保留当次，避免干扰小爽审读。
3. **全量核对**：写完后与上一版逐节比对，确保没漏重要信息（见 §6.4 版本沿革）。
4. **改动点汇报**：任何改动点都要主动告诉小爽（哪怕只是删冗余），小爽只查 ⚡️ 处，未标记即默认未改。
5. **规则单一来源**：硬性规则（如门禁字数）只在门禁节写一处，其他节引用不重复写，防改丢冲突。

#### 任务收尾五步清单（每次任务结束必做）

1. **更新任务规划**（`企业库任务规划_V*.md`）：完成移"已完成"、新增登"进行中"、遗留登"待办"。
2. **检查手册版本**：本轮有规则变化？有 → 升版本号。
3. **写 memory**：`.workbuddy/memory/YYYY-MM-DD.md` 记本轮做了什么。
4. **git 提交留痕**：所有改动 commit（不一定要 push）。
5. **汇报小爽**：做了什么 / 改了什么规则 / 部署了什么 / 遗留什么。
6. **【复盘检查项·2026-07-23 新增】**：①文档与代码是否核对过、有无要修正（§0 铁律）；②打标签时发现词表颗粒度问题 → 提建议给小爽；③遗留的存量问题（英文/模板/信息不足）进度同步。

#### ⚡️ 常遇遗漏问题清单（小爽与 AI 共同发现，提醒走查必查）

| 问题 | 表现 | 当前处理方式 |
|---|---|---|
| description 模板污染 | 多家同文模板话术（如"公司通过多渠道拓展市场"） | 走查子智能体查 BANNED 句 + 批量清洗 |

| deep_article_links 填充 | 当前全 0，未来可能有 | ⚡️ 列在预览表提醒，有则填、无则略（非强制） |

#### 文档版本校验

**写完 / 改完本文档后，必须和上个版本逐节比对**，确保没漏重要信息：
- 上版有的章节 / 规则 / 代码位置，本版是否保留或显式说明"为何移除"
- 本版新增的原则 / 修正，是否在正文和变更说明里都体现
- 字段字典、门禁规则、前端规则这类"易漏清单"逐项核对
校验发现遗漏 → 补回，再提交。

每月初（月度任务后）：主动检查 `_deprecated/` 下 1 个月前、确定不用的临时文件 → 删或续归档；根目录散落临时脚本移 `_deprecated/`（命名加 `企业库_` 前缀）。

### 6.3 常见坑

| 坑 | 表现 | 规避 |
|---|---|---|
| ⚡️ 评分公式/门禁版本错配 | 文档写四维、代码旧版三维；或门禁值对不上 | **以代码为准**；改规则同时改代码与文档，同一次 commit |
| 二次合并覆盖好数据 | 对草稿全量重跑覆盖已部署 recommend | 只用增量合并 |
| 自造平行规则 | 凭记忆写 `_quality_gate.py` 八条 | **只认 `check_single.py`** |
| 文档与代码脱节 | 文档写一套、代码另一套 | 任务前核对代码，发现错改文档 |
| 有动态排后 | last_news 四来源漏其一导致排序错 | 四来源必须全 |
| 模板污染 | 多家同文模板话术 | 批量走查清洗 |
| name vs name_cn | 误用 name_cn 展示 | 前端固定 name |
| desc_cn 停用 | 仍往 desc_cn 写 | 改读 description |
| Windows 部署坑 | git 换行 `\r` 致 Pages 404 / 大包代理超时 | deploy 脚本已处理，大文件进 .gitignore |
| ⚡️ 信号强度回填后 total_score 未重算 | 历史 total_score 用旧 sig 算，与当前 sig 不符 | 改 sig 或公式后必重跑 `merge_batch_scores.py` |

### 6.5 历史教训（写进流程）

1. 改文档不能把已定对的结论又改丢（每次新建议是叠加，不是覆盖）。
2. 清任务清单前必须先核实并登记，不得批量误清（金额万/亿、阶段4评分早已落地，曾误当摆设清掉）。
3. 文档与代码可能不一致——任务前必须核对代码，发现文档错（触发人可能是自己）要改文档。
4. 所有规则尽量融入流程带触发条件，不单独存放成死内容。
5. 写完文档跟上版校验，防漏信息。
6. ⚡️ 评分公式/门禁等"硬规则"一旦变更，必须**代码与文档同步改、同一次 commit**，避免两处漂移。
