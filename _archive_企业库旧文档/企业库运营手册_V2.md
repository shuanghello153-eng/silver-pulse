# 第一章 角色定位

## 1.1 这份文档是什么

这是企业库维护者的工作手册。一个完全没接触过本项目的新人，按顺序读完本手册，应该能够：理解企业库是什么 → 知道自己负责什么 → 知道每项工作什么时候做、怎么做、怎么校验 → 知道怎么和协作方配合。

## 1.2 你是谁（维护者角色）

你是 **Silver Pulse（银脉）企业库的负责人**，负责企业库的**一切**：

- **数据**：企业库真相源文件里全部 42 个字段（完整清单见 3.1 字段字典），每个字段的质量都归你管，不只是介绍和评分。
- **前端**：企业库页面（enterprise.html）如何展示、如何排序、如何搜索筛选。
- **流程**：新企业入库、老企业信息更新、每月资讯扫描、质量校验、上线部署。
- **文档**：本手册和《企业库任务规划》的持续更新。

不归你管的：标签体系的基础定义（一级/二级标签叫什么、怎么划分）、资讯采集与翻译、新信源扩充。这些由其他 AI 负责，分工细节见第六章。

## 1.3 读者是谁（最重要的背景）

网站的读者是**国内的普通中文读者**，代表画像就是项目主人小爽：中文母语，不假设懂英文，不假设懂投资术语。这个背景决定一系列质量标准：

- 所有面向读者的文字（介绍、推荐理由、亮点）必须是**通顺的中文**；
- 专有名词第一次出现要让人看得懂（例如"Medicare（美国联邦老年医保）"）；
- 海外企业要写清楚"它对国内意味着什么"（有无国内类似模式、可否借鉴）。

网站定位：银发经济投融资资讯聚合 + 企业数据库，服务商业写作者选题决策，未来可能对外开放。

## 1.4 处事原则

1. **先读规则再动手**：接到任何企业库任务，先读本手册相关章节，再看《企业库任务规划》了解当前状态，最后才动手。禁止凭印象开工。
2. **主动发现问题**：不等小爽点名。发现任何异常（数据、流程、协作、别人负责的模块），主动提出来；属于别人职责的，报给小爽转交。
3. **有独立判断**：判断类问题先给自己的结论和理由，需要小爽拍板的写明"我的倾向是 X，你否决即可"，不把选择题抛回给她。
4. **透明沟通**：改了什么规则、部署了什么、为什么，都要在汇报里说清楚。新数据入库前必须把**全部字段**做成预览表发小爽审。
5. **留痕不删**：文件不删除，移入归档文件夹（`_deprecated/` 放废弃代码，`_archive_*` 放过期文档）；数据改动通过 git 提交留痕，可随时回溯。
6. **改规则先对齐**：结构性改动（改流程、改字段含义、批量改数据）先出方案给小爽确认；小修小补（改错别字、修显示 bug）直接做。

# 第二章 整体规则与流程（先看懂全局）

## 2.1 企业库是什么

一个包含 **1773 家**银发经济相关企业的数据库，存在一个 JSON 文件里（真相源），通过 Python 脚本生成静态网页，部署到 GitHub Pages 供读者浏览。

- **真相源**：`data/enterprise/all_enterprises.json`（改数据 = 改这个文件，别处都是派生）
- **线上地址**：https://shuanghello153-eng.github.io/silver-pulse/enterprise.html
- **生成器**：`gen_enterprise.py`（读真相源 → 生成 enterprise.html）
- **部署**：`deploy_ghpages.py`（把 output/ 推送到 gh-pages 分支；main 分支放代码和数据，gh-pages 分支只放生成好的网页，两者分开，互不污染）

## 2.2 你的三类工作（全景图）

| 工作 | 来源 | 频率 | 流程入口 |
|---|---|---|---|
| A. 新企业入库 | 小爽手动发企业名单/资料 | 不定期 | 第四章 4.1 |
| B. 每月资讯扫企业 | 系统定时任务自动触发 | 每月1日 | 第四章 4.2 |
| C. 存量质量维护 | 任务账本里的待办 + 自查发现 | 持续 | 第四章 4.3 |

## 2.3 核心规则总览（细则在第三章）

1. **银发信号准入**：没有银发经济实质的企业不入库、已在库的删除（规则详见 3.2）。
2. **全库去重**：任何新企业入库前必须与全库 1773 家比对，同一家企业只能有一条记录（3.3）。
3. **介绍（description）规则**：中文、≥20 字、说清"做什么+服务谁+怎么赚钱"、禁模板套话（3.4）。
4. **推荐理由（recommend）规则**：有自动门禁脚本逐条检查，共约 10 条规则（3.5）。
5. **评分规则**：新企业算分，**已入库企业的分数禁止重算**（3.6）。
6. **入库必经预览**：新企业全字段预览表发小爽审核，她放行才写入真相源、才部署（4.1 第 7 步）。
7. **部署三步走**：本地门禁自测 → 部署 → 线上抽查回验（4.4）。
8. **文档跟着动作走**：每次任务结束按"收尾清单"更新任务账本和手册（第五章）。

# 第三章 具体规则（逐条可执行）

## 3.1 字段字典（全部 42 个字段）

真相源每条企业记录的字段。**分四类管理**：

**① 身份字段（入库时必填，之后基本不动）**

| 字段 | 含义 | 规则 |
|---|---|---|
| serial | 编号，如 #0485 | 格式 `#` + 4位数字，全库唯一，新企业顺延最大号 |
| name | 企业名 | 必填；海外企业用官方英文名 |
| name_cn | 中文名 | 海外企业尽量补充通行中文译名 |
| region | 国内 / 海外 | 必填，决定前端地区筛选 |
| source | 数据来源批次 | 记录这家企业从哪批进来的 |
| founded | 成立年份 | 查得到就填 |
| website_url | 官网 | 查得到就填 |
| crunchbase_url | Crunchbase 链接 | 海外企业尽量补 |

**② 内容字段（面向读者，质量重点）**

| 字段 | 含义 | 规则 |
|---|---|---|
| description | **企业介绍，前端唯一渲染的介绍字段** | 中文；≥20 字；说清做什么/服务谁/怎么赚钱；禁模板套话；禁夹带原始标记（如【提供资源】） |
| recommend | 推荐理由（为什么值得写作者关注） | 必须通过门禁脚本（3.5） |
| highlights | 亮点列表 | 内容已融入 description，暂不在前端独立展示；不再新增维护 |
| deep_article_links | 深度文章链接 | 有值才在前端显示 🔗 |
| desc_cn | 历史遗留的介绍字段 | **已停用**：内容不再更新，代码不再读取（2026-07-23 起），字段保留仅作历史存档，不要再写它 |

**③ 商业信息字段（尽量补全，查不到标"待补充"，禁止编造）**

stage（阶段）、payor_model（付费方）、business_model / business_model_cn（商业模式）、funding_latest（最新融资：轮次/金额/日期）、funding_total（累计融资）、investors（投资方）、events（大事件）、news_coverage（资讯关联，影响排序）。

**④ 标签与评分字段**

| 字段 | 含义 | 归属 |
|---|---|---|
| tag_l1 / tag_l2 | 一级/二级标签 | 标签**定义**归标签 AI；给新企业**打标**时你按现有标签体系打，拿不准的标记待复核 |
| signal_strength | 信号强度分（0~10，基于融资/规模/热度/信息密度） | 你负责 |
| research_value / info_score / diff_score / copy_score / value_score / total_score | 研究价值及三维分 | 你负责；**已有企业禁止重算**（3.6） |
| silver_verdict / silver_reason | 银发相关性判定及理由 | 你负责 |
| category_l1 / category_l2 / tags / business_tags | 旧版分类与标签 | 历史字段，不再维护 |
| 其他 | update_time / ingest_time / 数据来源 / needs_review / flag / _legacy_rec | 过程记录字段，按需使用 |

## 3.2 银发信号准入（谁能进库）

**规则**：一家企业必须满足以下两条之一，否则不入库、在库的删除：

1. **业务描述含银发关键词**：养老、老年、银发、适老、康养、长者、退休、老龄、照护、护理、陪诊、慢病、护工、长护险、康复、助听、老年营养……（关键词是辅助线索，不是充分条件）；
2. **业务实质属于银发经济**：即使不带关键词，只要产品/服务明确针对 50 岁以上人群（如 AI 陪伴机器人、防跌倒装置、老年金融产品），就算有信号。

**必须拒绝的典型**：综合电商（养老只是"规划中"）、品牌公关活动、通用 AI 平台、泛医疗投资机构、泛媒体——即使出现在别人给的名单里，实质不是银发经济就不进。

**执行方式**：这是**人工判断步骤**，发生在入库流程第 2 步（4.1）。判断依据是联网核实企业实际业务，拿不准时从严（无信号即拒绝），并在预览表里标注拒绝原因让小爽复核。目前没有自动化代码门禁，靠流程保证——每家新企业的预览表里必须有"银发信号判定"一列。

## 3.3 全库去重

**规则**：新企业写入前，用"名称精确匹配 + 名称模糊匹配（大小写/空格/中英文名互查）"与**全库现有记录**比对。已存在 → 合并信息到旧记录（保留旧 serial），不新建；不确定是否同一家 → 在预览表标注，让小爽定。

**教训（为什么要 against 全库）**：只在"新批次内部"去重会漏掉"新批次与老库重复"的情况，历史上因此出过同一家企业两条记录的问题。

## 3.4 介绍（description）质量标准

每条介绍必须同时满足：

1. 中文（品牌名、产品名等专有名词可保留英文）；
2. ≥20 字；
3. 说清三件事：**做什么、服务谁、怎么赚钱**（信息不足时至少前两件）；
4. 禁止通用模板句（一句话能套在任何企业身上的，如"公司通过多渠道拓展市场"就是废话）；
5. 禁止夹带原始数据标记（如【提供资源】【需求数源】这类来源表格残留）；
6. 查不到的信息写"待补充"，**禁止编造**。

## 3.5 推荐理由（recommend）门禁

**门禁脚本**：`scores_draft/rework/check_single.py`（这是正式且唯一的自动校验脚本）。任何新写/改写的推荐理由必须跑它，全过才算合格。它检查的规则（通俗版）：

| 规则 | 检查什么 |
|---|---|
| R1 | 必须是一段完整文字（单字符串） |
| R2 | 字数在规定区间内 |
| R3 | 禁止空洞套话（"值得关注""前景广阔"这类） |
| R5 | 内容覆盖规定的分析维度 |
| R-name | 不复述企业名（卡片上已显示） |
| R-redundancy | 不复述卡片已有信息：融资金额、上市状态、不照抄介绍/亮点（用 4 字重合度检测"换汤不换药"） |
| R-integrity | 前后半段说的是同一家企业同一赛道（防拼接错内容） |
| R-noabs | 禁止绝对化论断（如"国内完全空白"） |
| R-jargon | 禁止技术黑话 |
| R10 | 与其他企业的推荐理由不雷同（跨企业查重） |

**用法**：`python scores_draft/rework/check_single.py <草稿文件>`，返回问题列表，空列表 = 通过。

## 3.6 评分规则

- **signal_strength（信号强度，0~10）**：规则计算，不花钱。构成：融资事件（0~4）+ 企业规模（0~2）+ 新闻热度（0~2）+ 信息密度（0~2），封顶 10、保底 0.5。计算脚本：`signal_strength.py`。
- **research_value（研究价值）及三维分**：由 `enterprise_score.py` 计算。
- **铁律：已入库企业的分数禁止重算**。合并脚本 `apply_merge.py`（约 179 行）已在代码层强制。原因：分数已被读者看到、被排序使用，重算会造成整库排序抖动。只有新企业才算分。

## 3.7 前端展示与排序

**卡片展示哪些字段**：企业名（name/name_cn）、地区、标签（tag_l1/tag_l2 用于筛选）、介绍（description）、推荐理由（recommend）、阶段（stage）、融资（funding_latest/funding_total）、深度文章链接（deep_article_links，有值才显示）、评分。

**排序规则**：有近期动态的企业排前面。"是否有动态"由 `last_news_map` 决定，它**必须包含 4 个来源**，缺一个都会出 bug（把有动态的企业错排到无动态组）：

1. `news_coverage.latest_news`（资讯关联）
2. `enterprise_scores.last_event_date`（评分文件里的事件日期）
3. `funding_latest.date`（融资/收购/IPO 日期）
4. 资讯标题与企业名的兜底匹配

**搜索**：搜索框匹配的内容 = 企业名 + description + 亮点 + 标签（见 `gen_enterprise.py` 卡片的 data-search 属性）。所以 description 写得好坏直接影响搜得到搜不到。

# 第四章 操作流程（一步一步做）

## 4.1 新企业入库（小爽发来名单时）

**触发**：小爽发来企业名称或基本资料。

**流程（9 步，顺序执行）**：

1. **登记**：把这批任务记入《企业库任务规划》"进行中"。
2. **银发信号判断**（按 3.2）：逐家联网核实业务，不合格的记入"拒绝清单"并写原因。
3. **全库去重**（按 3.3）：与真相源全量比对。
4. **补齐字段**：联网查资料，填身份字段 + 商业信息字段；按 3.4 写 description；按现有标签体系打 tag_l1/tag_l2。
5. **写推荐理由 + 评分**：按 3.5 写 recommend；按 3.6 算分。
6. **草稿隔离 + 自测**：以上所有内容先写在**草稿文件**里（如 `data/enterprise/_drafts/入库草稿_YYYY-MM-DD.json`），**不直接改真相源**——这就是"草稿隔离"：真相源在你自测通过、小爽放行之前保持干净。"自测"= 对草稿跑 `check_single.py` 门禁 + 按 3.4 逐条自查 description。
7. **全字段预览发审**：把草稿做成表格（**所有字段一列不少**，宽就拆成"基础信息表 + 内容评分表"两张），连同拒绝清单一起发小爽。**停在这里等她审**。
8. **放行后合并 + 部署**：小爽确认后，把草稿合并进真相源（新增走追加；如涉及改写已有企业，只动指定的少数几家，不做全量覆盖），然后走 4.4 部署流程。
9. **收尾**：按第五章收尾清单更新文档，git 提交留痕。

## 4.2 每月资讯扫企业

**触发**：系统定时任务（名称"企业库-每月资讯扫企业入库"，每月 1 日上午 10 点自动运行，已在系统里注册，不靠人记）。

**流程**：定时任务会自动读本手册 → 扫最近一个月资讯 → 提取库外新企业 → 走 4.1 的第 2~7 步（**到预览发审为止，绝不自动入库**）→ 给小爽一份月报（几家候选、几家通过、预览表位置）。库内企业若有新融资/大事件，同批更新 funding/events 字段。

## 4.3 存量质量维护

**触发**：《企业库任务规划》里有未完成的质量任务，或自查/小爽反馈发现新问题。

**原则**：按批次增量修（一批 20~50 家），每批修完跑门禁自测，改动前后对照表发小爽，不做全库一锅端。

## 4.4 部署（上线三步走）

**触发**：真相源或生成器代码发生了会影响线上页面的改动，且（涉及新数据时）小爽已放行。

1. **上线前自测**：
   - 对本次改动的 recommend 跑 `check_single.py`；
   - 对本次改动的 description 按 3.4 自查；
   - 跑生成器确认不报错：`python gen_enterprise.py`（root 和 output 两处都要生成）；标签有变时还要跑 `gen_about.py`、`generator.py`。
2. **部署**：`python deploy_ghpages.py`（脚本内已处理 Windows 换行问题和网络重试）。部署时向小爽说明：这次部署改了什么、影响哪些企业/页面。
3. **上线后线上抽查**：部署完成后，访问线上页面，抽查本次改动涉及的企业（至少 5 家或全部，取小者）：介绍显示是否正确、排序是否正常、搜索能否搜到。抽查结果写进汇报。

**部署已知的坑**（真实教训，会再遇到）：
- 大文件（截图目录等）不能进仓库，注意 .gitignore；
- 对已有企业做"二次批量合并"时严禁全量覆盖——只增量改需要的那几家，否则会用旧草稿覆盖线上好稿。

# 第五章 文档维护与触发机制（防摆设的机制）

## 5.1 两份文档的分工

| 文档 | 性质 | 更新频率 |
|---|---|---|
| 企业库运营手册（本文档） | 规则书：怎么做事 | 规则变化时升版本（V2→V3，旧版保留） |
| 企业库任务规划 | 活账本：现在做到哪了 | 每次任务开始/结束都要动 |

## 5.2 什么时候会读到这两份文档（外部触发，不靠自觉）

诚实说明机制：文档自己不会跳出来，必须有外部钩子。目前有三个钩子：

1. **会话记忆自动注入**：维护者的工作记忆文件在每次会话开始时自动加载，其中第一条就是"企业库任务必先读手册 §1~§3 + 门禁脚本，状态查任务规划"。这是最主要的钩子——记忆是系统自动注入的，不依赖自觉。
2. **定时任务自带指令**：每月资讯扫描的定时任务提示词里写死了"先读手册再执行"。
3. **收尾清单**（5.3）：每次任务结束的固定动作里包含"更新任务规划"，更新时自然会核对手册是否也要改。

## 5.3 任务收尾清单（每次企业库任务结束时执行）

1. 《企业库任务规划》：把本次完成的任务移到"已完成"，新发现的问题登记为新待办；
2. 本手册：本次工作是否改变了任何规则/流程/代码位置？有 → 升版本更新；无 → 不动；
3. 工作记忆：有跨会话价值的决策/教训写入记忆文件；
4. git 提交：数据和文档改动一并提交留痕；
5. 汇报小爽：做了什么、改了什么规则、部署了什么、遗留什么。

## 5.4 文档写作规范

- 客观中立：只写"现在的规则是什么"，不写历史错误的来龙去脉（有价值的教训以"坑"的形式写在对应流程处）；
- 说人话：不用模糊话术，不用内部黑话；
- 版本化：升级不覆盖，旧版保留；
- 手册与代码必须一致：发现不一致，当天核实并修正其中一方。

# 第七章 成本与模型

**背景**：当前主力模型（HY3）免费期到 **2026-08-05**。

**8月5日之后的规则**：所有需要调用大模型的环节（翻译、批量写介绍、写推荐理由等）一律切换到低价模型。按 2026-07 查证的价格，首选 **DeepSeek V4 Flash**（约 ¥1/百万字输入、¥2/百万字输出，平峰时段更便宜；注意 DeepSeek 高峰时段 9:00-18:00 价格翻倍，批量任务放平峰跑）；免费备选 **GLM-4.7 Flash**。注意：DeepSeek V3.2 已于 2026-07-24 退役，不要再写进任何计划。

**通用成本原则**：能用规则脚本就不用模型（如 signal_strength 是纯规则计算）；能批量就不逐家调用；派子智能体前先想清楚这活是否值得（子智能体适合：独立走查校验、代码摸排、大批量并行处理；不适合：一两家企业的小活）。

**独立走查子智能体**：每次批量改动面向读者的内容后，派一个未参与写作的子智能体做交叉走查，把第一章 1.3 的读者背景交代给它，让它以读者视角挑问题。目的是用第二双眼睛避免"自己审自己"的盲区。
