## 1. 网站定位

Silver Pulse（银脉）= 银发经济投融资资讯聚合 **+ 企业数据库**，本质是小爽的**"选题情报台"**——让小爽早上打开网站，一眼看到"今天哪些企业 / 资讯值得写深度稿"。未来可能对外开放。

> 它不是资讯汇编站，是给小爽自己用的**选题决策工具**。每家企业 / 每条资讯的终点问题都是：中国银发经济创业者能从中借鉴什么？

## 4. 整体工作流程

### 4.1 概括介绍

所有任务走**同一套流程**，只是"从哪进、走到哪停"不同。不存在三套独立流程，不要抄三遍。

### 4.2 需求来源与分支

主要需求来源有三类（**注意：这不是穷尽规则，任何临时小需求——比如 UI/UX 微调——都可以走轻量分支，不必写死**）：

| 来源 | 走哪条流程 | 说明 |
|---|---|---|
| **A. 小爽给企业名单** | → 新企业入库（完整 1→10 步） | 最常见 |
| **B. 每月资讯扫描发现** | → 并入 A（新企业入库完整步） | 每月1日23:00扫描发现的新企业走完整入库流程，HY3免费期至 2026-08-05；之后强模改用 DeepSeek V4 Flash |
| **C. 存量走查发现问题** | → 从**步骤 3（补全字段）**起跳，跳过步骤 1–2（准入/去重已做过） | 例：英文 description 待译、模板话术待清、漏打标 |
| **D. 外部 AI 交接** | → 信源扩充 AI / 其他 AI 交来**企业名单** | 见 §4.5 交接协议 |

- **轻量分支**：纯 UI/UX 小改动（搜索框跳动、placeholder 文案等）可走"前端校验→直接部署→事后补审"，不必走完整审核关卡（见 5.9）。

### 4.3 详细步骤（一条主流程，编号 1–10）

> 来源 C 从步骤 3 起；轻量 UI 改动可只走步骤 6→9 并事后补审，跳过8。

1. **银发相关性判断（入库准入）** —— 无信号直接删，不进库
2. **全库去重** —— 对 `all_enterprises.json` 全量比对（⚡️ **先跑关键词粗筛脚本，再 AI 精比对**）
3. **补全所有字段** —— 联网/翻译补齐，重点：description / 标签 / 评分键 / 商业字段（⚡️ **补字段时记录引用网址**）
4. **写推荐理由（recommend）** —— 强模产出
5. **算评分** —— 信号强度（脚本）＋ 四维精评
6. **前端展示校验** —— 跑生成器，肉眼看卡片渲染
7. **质量门禁自测** —— 跑门禁脚本 + 子智能体走查
8. **小爽审核** —— 发全字段预览表 + ⚡️ **审核附言（必写）**，硬卡点
9. **合并部署** —— 编辑真相源 → 生成 → 部署 gh-pages（⚡️ **可用编排脚本一键跑**）
10. **上线走查 + 抽查** —— 派子智能体走查，问题回滚

### 4.4 流程衔接说明（⚡️ V7.4 更新：脚本节点已串联）

#### 4.4.1 各环节衔接方式总览

整体流程是**「文档编排 + 代码工具」混合模式**。核心设计原则（⚡️ V7.4 明确）：

> ⚡️ **把节点分成两类：「AI 必须介入的节点」和「纯脚本节点」。相邻的纯脚本节点用编排脚本串成一条命令，AI 只在必须介入的节点动脑。** 这样 AI 的调用次数 = 语义判断次数，中间数据传递不再消耗对话轮次和积分。

| 步骤 | 节点类型 | 衔接方式 | 说明 |
|---|---|---|---|
| **步骤 1a 初筛** | 纯脚本 | `config.SILVER_STRONG_KEYWORDS` 强词命中检测 | 已脚本化，命中→进二筛，未命中→拒 |
| **步骤 1b 二筛** | **AI 必须介入** | AI 低模是非题判断 | 银发相关性实质判断 |
| **步骤 2a 去重粗筛** | 纯脚本 | ⚡️ **`dedup_keyword_prescreen.py`（已建）** | 核心词全库匹配，排除明显不重复的 |
| **步骤 2b 去重裁决** | **AI 必须介入** | AI 对"疑似重复候选"做信息增量比对 | 只看粗筛命中的候选，工作量大减 |
| **步骤 3 补全字段** | AI 为主 | AI 联网/翻译；⚡️ 引用网址顺手记录（供 `collect_source_urls.py` 统计） | 缺值标"待补充" |
| **步骤 4 推荐理由** | **AI 必须介入** | AI 强模产出 | 纯写作，无脚本 |
| **步骤 5 评分** | 纯脚本 | `signal_strength.py` + `merge_batch_scores.py` | 确定性计算 |
| **步骤 6 前端生成** | 纯脚本 | `gen_enterprise.py` | 一键生成 |
| **步骤 7 关卡1 门禁** | 纯脚本 | `check_single.py` + `check_description.py` | D1-D4 + R 系列 |
| **步骤 7 关卡2 走查** | **AI 必须介入** | 子智能体语义走查（≤2 轮） | ⚡️ 三维真判断检查在此（R5 删除后由这里负责） |
| **步骤 8 小爽审核** | **人工卡点** | 预览表 + 审核附言 | 永不自动化 |
| **步骤 9 合并部署** | 纯脚本 | ⚡️ **`enterprise_build.py --deploy`（已建）** | 门禁→备份→增量合并→生成→部署一条命令 |
| **步骤 10 走查** | AI + 人眼 | 子智能体 + 抽查 | 语义判断 |

#### 4.4.2 ⚡️ 编排脚本 `scripts/enterprise_build.py`（V7.4 新建）

回答小爽"能否把脚本 A 的产出直接固化给脚本 B，AI 只调一次"的问题：**能，且已做**。

```
用法：
  python scripts/enterprise_build.py --candidates 候选.json            # 门禁自测（不合并）
  python scripts/enterprise_build.py --candidates 候选.json --merge    # 门禁→备份→增量合并→生成
  python scripts/enterprise_build.py --candidates 候选.json --merge --deploy  # 以上 + 部署
串联内容：check_single(R系列) + check_description(D1-D4) + R10 跨企业比对
        → all_enterprises.json 自动 .bak 备份 → 按 serial 增量合并（只更新候选字段）
        → gen_enterprise.py + generator.py 重生成 output/
        → （仅加 --deploy 时）deploy_ghpages.py
```

**质量不受影响的原因**：串联的全部是确定性节点（门禁/合并/生成/部署），语义判断节点（二筛/写作/走查/审核）仍由 AI/小爽逐个把关。**默认不带 --deploy**，步骤 8 小爽放行后才加部署参数——人工卡点原样保留。

#### 4.4.3 流程不会卡住的保障

**原则：每个步骤都有明确的"输入→输出→下一步"定义。如果某步卡住：**
- **脚本报错** → 检查输入数据格式，看报错信息修数据，重跑
- **AI 判断拿不准** → 标记"待小爽定"，进入步骤 8 让小爽拍板，**不阻塞后续其他企业**
- **子智能体超时/质量差** → 换一种方式表达 prompt，或自己先做一遍再让它复查
- **小爽驳回** → 见步骤 8 的驳回流程（§5.7），有明确回退路径

**关键设计：单家企业不阻塞批量。** 如果一批 20 家中有 3 家有争议，先把 17 家推到下一步，3 家标记"待定"单独处理。

#### 4.4.4 后续衔接约定

每个步骤的"接棒"靠本手册的编号步骤驱动；确定性操作直接调对应脚本（首选编排脚本一条命令）；语义操作（判断/写作/审核）由 AI/小爽人脑完成。新人/新 AI 看 §4.3 编号即可知道"现在该干嘛、调什么脚本"。

### 4.5 外部 AI 交接协议（⚡️ V7.4 升级为"名单交接制"）

#### ⚡️ 职责分界（V7.4 明确，回答"为什么你不能直接去爬整个网站"）

- **联网搜集某家企业的资料**（搜索→打开若干页面→提取信息）：企业库 AI 的日常能力，按需做。
- **把某个网站的全部企业名录成体系爬下来**（翻页、反爬、批量抽取、结构化落库）：这是**爬虫任务**，需要专门写爬虫代码、处理站点结构，不是"搜集资料"的同一种能力。该活归**信源扩充 AI / 爬虫脚本**，企业�� AI 不越界去爬整站。
- 两者分工：**信源侧负责"发现企业、交名单"；企业库侧负责"判断入库、怎么入库"。**

#### ⚡️ 名单交接标准（V7.4 新增）

信源扩充 AI（或其他 AI）交来的应当是**企业名单**，每家至少含：

```
企业名称（必填） | 官网或来源 URL（尽量） | 地区（尽量） | 银发信号初判一句话（尽量） | 已知基础信息（有就给：融资/业务/成立年份）
```

**入不入库、怎么入库，由企业库 AI 全权判断**（走 §4.3 完整流程）。信源 AI 不需要也不应该替企业库做准入判断——它给的初判只是参考。

#### 接收动作

```
1. 接收结构化文件（JSON/Excel），放入 handoff/enterprise_inbox/
2. 从步骤 1 开始走完整入库流程（不跳步）
3. 完成后产出结果放 handoff/enterprise_outbox/
4. 需要反馈信源 AI 的（比如某家不该入库、某个信源质量高值得转正），写跨 AI 笔记（见 §4.6）
```

**为什么不定死"必须通过某个目录交接"**：AI 可能换、上下文可能断。核心原则是**"拿到名单→按手册走流程→产出结果"**，交接文件是异步的、持久的（文件系统比对话窗口可靠）。

### 4.6 ⚡️ 多 AI 协作共享区（V7.4 新增）

**位置**：`handoff/cross_ai_notes/`（格式规范见目录内 README.md）

**用途**：任何 AI 在干自己的活时发现了别的 AI 职责范围内的问题/机会（例：企业库补字段时发现某网站值得当信源；信源 AI 发现某企业疑似重复），写一条笔记留言，**不打断对方、不越界代办**。

**笔记格式**：文件名 `YYYY-MM-DD_来自XX_给_目标AI_主题.md`，头部标 `to:/from:/date:/status:`（pending→done）。

**查看机制**：每个 AI 设**每周自动化任务**跑 `python scripts/cross_ai_digest.py --ai 自己的名字`，列出给自己的待处理笔记 → 处理 → 把 status 改 done → 有需要就汇报小爽。企业库 AI 的周任务已建（每周一 9:00，automation-1784882846607）。

## 5. 每步骤详细规则（与步骤编号一一对应）

### 5.1 步骤 1 · 银发相关性判断（入库准入）——两阶段

> **定位**：这是"入不入库的门槛"，它只产出"通过 / 拒绝"。两阶段：初筛(脚本) + 二筛(AI 判断)。

#### 阶段一 · 初筛（强词脚本，已脚本化）

**现有脚本资源**：`config.SILVER_STRONG_KEYWORDS`（约 67 个中英文强词列表），被 `selection/relevance_screener.py` 的 RuleBasedBackend 使用。

**调用方式**：
```python
from config import SILVER_STRONG_KEYWORDS
text = (name or "") + " " + (description or "")
hit = any(kw in text for kw in SILVER_STRONG_KEYWORDS)
# hit=True → 进入阶段二；hit=False → 直接拒绝（除非有特殊理由）
```

### 5.4 步骤 4 + 5 · 评分与推荐理由

**评分架构（阶段 1–2 为"银发相关性判断 / 准入"，见 5.1；阶段 3–4 为本步骤的评分）：**

- **阶段 3 · 信号强度（脚本 `selection/signal_strength.py`，0~10，封顶 10 保底 0.5）**，企业与资讯共用同一函数 `compute_signal_strength()`，按事件分级换算：
  - 信源起点：T1=0.5，T2=0.3，T3=0.1
  - IPO = +6；融资（海外美元）：≥10亿=5 / 1亿=4 / 5000万=3 / 1000万=2 / 500万=1 / 100万=0.5
  - 融资（国内元）：≥10亿=6 / 1亿=5 / 5000万=4 / 1000万=3 / 500万=2 / 100万=1 / 50万=0.5
  - 收购（海内外）：≥100亿=6 / 50亿=5 / 10亿=4 / 1亿=3 / 5000万=2 / 1000万=1
  - 时效：近1周=2.5 / 近1月=2 / 近2月=1.5 / 近半年=1 / 近1年=0.5 / 更久=0.25

- **阶段 4 · 强模四维精评**：输出 `recommend` + 四维评分

**四维评分公式（total_score，代码 `merge_batch_scores.py:66-72` 实现）：**
```
total_score = 信号强度 × 30% + 信息量 × 30% + 差异化 × 20% + 可复制 × 20%
```

**评分范围铁律（代码已实现防御性封顶）：**
- 每个维度（信号/信息/差异/复制）：**0 ~ 10 分**，超过 10 分取 10 分
- total_score：**0 ~ 10 分**（四维加权求和后封顶 10）
- **内部存储和计算全部用 0~10 分制**
- **前端展示时统一 × 10** → 显示值范围 0~100（见 `gen_enterprise.py:357`）
- 这样评分者从 0~10 打分更直观，不用从 0~100 里硬凑

**推荐理由（recommend）写法：**
- 用一段自然流畅的话，把**信息量 / 差异化 / 可复制**三方面判断融进去讲（信号强度已在列表展示为评分徽章，推荐理由里不复述），不刻意分段、不逐维列分。
- 写完后自检：**卡片/列表已展示的结构化信息**（融资金额、轮次、标题、摘要、来源、日期等）推荐理由里**不再重复陈述**。
- 不写"死规则"式套话；要有洞察（为什么这家值得写）。
- 与 description 明确分工：description 讲"它是谁、做什么"（基本事实），recommend 讲"为什么值得写"（判断洞察）。**基本事实放 description，判断放 recommend，两者不重复。**
- **禁止机械式地写"信息量：xxx；差异化：xxx；可复制：xxx"这种三段式**——要融成自然的一段话，让读者（小爽）读起来像在看一个编辑的真判断，而不是在填表格。⚡️ **V7.4 补充：正因为要防"机械凑词"，R5 关键词覆盖门禁已删除——凑词过门禁反而制造模板腔。三维是否有真判断，由关卡 2 子智能体做语义检查。**

#### 关卡 2：派独立走查子智能体（循环机制）

派一个 general-purpose 子智能体，给它以下指令：

> 你是企业库质量走查员。
> 请检查这批新企业的数据质量，重点关注：
> 1. **description 与 recommend 一起查**：description 是否大部分为中文、是否说清三件事（做什么/服务谁/怎么赚钱）、是否模板套话、与 recommend 是否重复；recommend 是否满足门禁规则（不为空、非套话、不雷同、有真判断、不复述 description 基本事实）；
> 2. **recommend 三维度检查（⚡️ R5 删除后这是三维检查的唯一防线）**：是否真的给出了信息量（素材够不够挖）、差异化（有什么独特之处）、可复制（国内能学什么）的有理有据判断？还是只在凑字？**不要看是否出现了"信息量/差异化/可复制"这几个词，而要看实质内容是否覆盖了这三个方面。**
> 3. 两者信息是否重复（recommend 不应复述 description 已有的基本事实）；
> 4. 银发信号判定是否合理（真的跟银发经济相关吗）
> 5. 字段是否齐全（尤其是 description / source / ingest_time）
> 6. 标签是否在 `_l2_l1.json` 词表中
>
> 输出一份问题清单（企业名 + 字段 + 问题 + 建议修改）。

**子智能体走查循环：**

```
第一轮走查 → 主智能体（你）修复问题
    ↓
第二轮走查（另一个子智能体或同一个重新跑）
    ↓ 有问题 → 主智能体再修 → 最多两轮
    ↓ 通过 → 进入关卡 3
```

**规则**：
- 子智能体**最多走查 2 轮**（避免无限循环浪费积分）
- 每轮之间由**主智能体（你）**负责修改，不是让子智能体自己改
- 如果 2 轮后仍有问题，标记"待小爽定"，进入步骤 8 让小爽裁决

**子智能体反馈的问题，你自己先修。能修的自己修，不确定的标记出来。**

#### 关卡 3：自己审一遍

自己作为第二双眼睛再过一遍：
- 打开生成的预览表（CSV/Excel），逐行看
- 重点检查：刚才子智能体发现的问题是否修好了、有没有漏网的
- 确认字段齐全、格式正确

发**全字段预览表 excel**给小爽，包含新企业的**全部字段**（不只是几个核心字段），按照重要程度排序列表顺序。

- recommend（全文）

- funding_latest, `funding_total`, investors, payor_model

#### ⚡️ 审核附言（V7.4 新增，必写）

发预览表时**必须同时附一段"审核附言"**，不能只甩表格。附言包含三部分（没有就写"无"，不许省略这一段）：

1. **遇到的问题**：本轮处理中碰到但表格里看不出来的问题（例：某两家疑似重复但证据不足拿不准、某家融资信息两个来源矛盾）
2. **需要协助的地方**：需要小爽拍板或提供信息的点（例：某家到底算不算银发、某个信源要不要转正）
3. **建议**：流程/体系层面的建议（例：建议新增某个二级标签、建议某类企业以后统一怎么处理）

**发给小爽，等她确认"可以入库"后才进行下一步。**

#### 驳回处理流程

如果小爽审核后发现问题的处理路径：

| 问题类型 | 处理方式 | 谁来做 |
|---|---|---|
| **个别企业信息有误** | 修改对应字段 → 重跑门禁 → 更新预览表 → 重新提交该企业 | 主智能体（你） |
| **多家企业共性问题**（如推荐理由风格统一有问题） | 批量修改 → 全部重跑门禁 → 更新预览表 → 重新提交 | 主智能体（你） |
| **规则理解分歧**（如某家到底算不算银发） | 给出你的判断+理由，提交小爽拍板 | 讨论 |
| **流程性问题**（如某个步骤应该加检查） | 记录下来，本轮先继续，下轮更新手册 | 记忆/文档 |

**关键原则：驳回 ≠ 从头再来。** 只修有问题的部分，没问题的不动。修完后**安排另一个子智能体复核**（不算在"最多 2 轮走查"限额内，这是审核后的额外验证），确认无误后再部署。

### 5.10 ⚡️ 文档维护机制（V7.4 重写为步骤式：先流程、后解释）

> ⚡️ **写法约定（小爽 2026-07-24 定）**：先给"什么时候做什么"的动作清单，解释和原理放后面分节详述。**本节规范适用于所有文档**（运营手册、行为准则、任务规划等），不只是本手册。

#### 流程 A · 平时改代码 / 改文档（每次触发必走）

```
1. 改代码前 → 先读手册对应章节，确认文档写的规则是什么
2. 改文档前 → 先读对应代码，确认代码实现的是什么
3. 发现两边不一致 → 判断哪边是"经确认的最新版本"（不一定代码就对！）：
   - 代码新、文档旧 → 改文档跟上代码
   - 文档是小爽最新确认的、代码旧 → 改代码跟上文档
   - 都不确定 → 问小爽
4. 代码与文档同一次 commit 提交（硬规则变更必须两边同改）
5. 本轮不改的不一致 → 收尾清单登记"待处理：文档代码不一致[位置]"
```

#### 流程 B · 发新版手册（规则变化时触发）

```
1. 判断版本号：功能变更(增删步骤/流程重构/公式变) → 大版本 +1（V7.4→V8.0）
              修正优化(门禁值/文字/bug修) → 小版本 +0.1（V7.4→V7.5）
              纯错字格式 → 不升版本直接改
2. 顶部写更新栏：日期 + ⚡️ 改动点列表（每条注明正文详址）
3. 正文标记：本次新增/修改文字用 ⚡️ + 加粗；同时删掉上一版的 ⚡️ 标记（小爽只查 ⚡️ 处）
4. 与上一版逐节比对：上版有的章节/规则/代码位置，本版保留或显式说明"为何移除"；
   字段字典、门禁表、前端字段表这类"易漏清单"逐项核对；发现遗漏补回再提交
5. 版本沿革（§6.4）补一行
6. 旧版移入 _archive_企业库旧文档/；企业库运维/ 只留最新版 + 任务规划 + 行为准则
7. MEMORY.md 更新"当前最新版本号"
8. ⚡️ 做四问复盘（V7.4 新增，见流程 D）
```

#### 流程 C · 任务收尾五步（每次任务结束必做）

```
1. 更新任务规划（企业库任务规划_V*.md）：完成移"已完成"、新增登"进行中"、遗留登"待办"
2. 检查手册版本：本轮有规则变化？有 → 走流程 B
3. 写 memory：.workbuddy/memory/YYYY-MM-DD.md 记本轮做了什么
4. git 提交留痕：所有改动 commit（不一定要 push）
5. 汇报小爽：做了什么 / 改了什么规则 / 部署了什么 / 遗留什么 / ⚡️ 问题与建议（同步骤8附言精神）
```

#### 流程 D · ⚡️ 手册调整后的四问复盘（V7.4 新增）

每次手册升版本，在汇报小爽时附四问答案，并把结论沉淀到对应层（能进流程的进流程，属源头思维的进《企业库行为准则.md》）：

```
1. 这次调整解决了什么问题？
2. 这个问题当初为什么会发生？（挖根因，不停在表面）
3. 为什么现在才被发现？（发现机制哪里失灵）
4. 以后如何从源头避免？——落在哪一层：流程规则 / 门禁脚本 / 行为准则
```

#### 流程 E · 归档清理（月度）

每月 7 日 23:00（自动化或手动）：`_deprecated/` 下 1 个月前、确定不用的临时文件 → 删或续归档；根目录散落临时脚本移 `_deprecated/`（命名加 `企业库_` 前缀）。

---

#### 解释与原理（对应上面各流程）

**为什么"不以代码为准一刀切"（流程 A 第 3 条）**：代码也可能错——V7.3 修复的排序键 bug（排序用了过时的 research_value）就是代码错、文档对的实例。要以"经过判断的最新正确版本"为准。

**什么时候更新本文档（流程 B 的触发条件）**：规则变了（小爽确认）→升版本；发现文档与代码不一致→走流程 A；新增/废弃字段→更新 §6.1；流程增减步骤→更新 §4；每次任务结束→按流程 C 检查。

**规则单一来源原则**：硬性规则（如门禁字数）只在门禁节（§5.6）写一处，其他节引用不重复写，防止两处不一致时改丢冲突。

**复盘检查项的归属**（不集中列大表，已拆入对应模块）：文档代码一致性→流程 A；打标签词表校验→§5.3；存量问题进度→§5.7 预览表；版本校验→流程 B 第 4 步。

> ⚡️ **V7.3 的"常遇遗漏问题"清单已删除**（V7.4）：其中每一条的解决方案都已内嵌到对应步骤的门禁/检查/流程约束中（模板污染→D3+走查；标签校验→§5.3；增量合并→§5.8；评分重算→§5.4 等），清单本身不再有独立价值。历史坑的完整对照仍可查 §6.3。

### 6.5 历史教训（写进流程）

1. 改文档不能把已定对的结论又改丢（每次新建议是叠加，不是覆盖）。
2. 清任务清单前必须先核实并登记，不得批量误清（金额万/亿、阶段4评分早已落地，曾误当摆设清掉）。
3. 文档与代码可能不一致——**任务前必须核对代码，发现文档错要改文档，发现代码错也要改代码**（V7.3 排序键 bug、V7.4 check_description 误标待建都是证明）。
4. 所有规则尽量融入流程带触发条件，不单独存放成死内容。
5. 写完文档跟上版校验，防漏信息。
6. 评分公式/门禁等"硬规则"一旦变更，必须**代码与文档同步改、同一次 commit**，避免两处漂移。
7. 不要盲目相信"代码为准"——代码也可能是旧的/错的。要以"经过判断的最新正确版本"为准。
8. ⚡️ **门禁不是越多越好**：机械化门禁可能诱导 AI 为过关而凑词，反而制造它要防的问题（R5 教训）。加门禁前先问：这条规则会不会改变产出行为的方向？语义质量问题优先交语义走查，不硬写成关键词规则。
