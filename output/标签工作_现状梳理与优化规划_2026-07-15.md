# 银脉标签工作 · 现状梳理与优化规划（2026-07-15 研究员版）

> 本文是我接手标签工作前的完整梳理。所有数字均来自对线上真相源 `data/enterprise/all_enterprises.json`（1305 家）与代码的实测，不盲信交接文档。原文档（V3 全映射、评分规则、TAGGING_RULES.md）**一字未改**。

## 0. 一句话结论

标签库"表面健康、底层有疾"：**9/10 校验项全绿，但 73% 企业只有 1 个标签、164 家企业（12.6%）共用假描述、8 个大桶≥40 家未真查、config 与数据已漂移、连"最新的"V3 文档都比线上库落后一个版本。** 修复路径清晰，但必须先对齐"要不要重洗 description"这一结构性决策，再动手。

## 一、我们在做什么 / 现状 / 目标

**做什么**：给银发经济企业库（1305 家）的每家企业打"一级+二级标签"，让用户在前台按标签筛选、快速判断值不值得细看；标签同时喂给评分的"可复制"维度。

**现状（实测线上库）**：
- 企业 **1305** 家；一级 **10** 个；二级 **108** 个（config 列了 109，多一个无数据的"抗衰"）。
- 0 标签企业 = 0；超 3 标签 = 0（硬约束达标）。
- 每家企业标签数：**952 家只有 1 个（73%）、302 家有 2 个（23%）、51 家有 3 个（4%）**。
- 大桶（≥40）：居家护理 90 / 陪伴服务 75 / 助听器 63 / 助行器 58 / 养老机构 47 / 兴趣社群 43 / 可穿戴监测 41 / SaaS 40。

**目标（我理解的小爽要的样子）**：
- 标签**易懂、能筛、有区分度**（小爽原话：太多=没特点，太少=不值得存在）。
- 每家企业至少 2–3 个**有信息量**的标签（跨领域视角），而非 73% 单标签。
- 大桶被真查真拆，模板污染被根除。
- 文档与线上库**永远同步**（文档是代码的派生，不是真相）。

## 二、我对标签的理解（补充小爽的观点）

小爽的两点完全正确，我补三点让它更可执行：

1. **标签是"做了什么 / 服务谁"，不是"用了什么技术"**。一家助听器公司和一家陪诊平台都"用了 SaaS / 有 AI"，但这不让他们相似。所以 `SaaS`/`AI`/`智能硬件` 这类"横切属性"当标签价值极低——它们该是业务模式元数据，不是筛选词。这是当前 8 个大桶里至少 4 个（SaaS/AI/智能硬件/可穿戴监测）虚胖的根因。
2. **标签要服务"可复制"判断**。阶段 4 要回答"国内有没有同类赛道"，标签若打错（把真保健品塞进医疗服务），推荐质量直接崩。
3. **多标签不是凑数，是视角**。单标签=只从一个角度看企业。一家助听器企业同时是 `消费品+智能硬件+听力健康`，三个标签分别回答"卖什么行业/什么技术/什么需求"，缺一不可。

## 三、标签是怎么筛出来的（还原真实链路 + 批判）

小爽描述的方法是：(a) 挑企业多的 L1/L2 逐家走查；(b)(i) 关键词聚类到最小颗粒 L2；(ii) 二次聚类给"不落入已有 L1"的第二个 L2；(iii) 同义合并、常用词做规范标签、其余进同类词。

**实测代码后，真实的落地是**：
- 引擎是 `config.py` 的 `ENTERPRISE_CATEGORIES`（108 个 L2）+ `data/enterprise/_l2_l1.json`（L2→L1 映射）+ `validate_tags.py`（9/10 校验门）。
- 打标主逻辑在 `_rebuild_tags.py`（207KB），本质是**脚本化的"关键词→标签"映射** + `BRAND_OVERRIDE`/`MISLABEL_FIX` 手工修正清单，**不是逐家企业 LLM 理解**。
- 那 164 家"模板文案"强烈暗示：前序 AI 先用 LLM 生成了结构化描述（"面向银发人群的X企业，主营Y业务：…"），再让关键词分类器**读这些描述回灌标签**——描述写"居家照护"就被标"居家护理"。

**这就是核心设计缺陷——自证循环 + 单点污染**：
- 标签质量取决于假描述的用词，而非真实业务。
- 同一条模板被分散标成 5 种不同标签（实测：17 家同模板 → 护士上门 8 / 居家护理 7 / 居家医疗 3 / 专业护理 2 / 安宁疗护 1）。
- "二次聚类补第二标签"在代码/数据里基本没落地（73% 单标签），说明那次补标要么没落库、要么被后续重跑覆盖。

## 四、我发现的问题（8 项，带证据）

**P1 · 文档已滞后于线上库（验证"交接文档不可全信"）**
- V3 文档称 107 个二级标签、缺 `出行助老`；线上实为 **108**（含 v15.1 新增的出行助老 4 家）。
- V3 文档：居家护理=99、兴趣社群=51；线上实为 **90 / 43**（v15.1 的清洗未反映进文档）。
- 结论：**文档是代码的派生物，会过期。以后以 `all_enterprises.json` 为准，文档每次改完必须重生成。**

**P2 · 73% 企业只有 1 个标签（"多标签"能力缺失）**
- 952/1305 单标签。V3 文档声称"单标签率降到约 51%（补标 112 家）"——与线上严重不符。多标签能力在数据中基本不存在。

**P3 · 164 家模板污染（12.6%，病根）**
- 20 条 boilerplate 描述被 164 家企业共用。典型：
  - 33 家："主营助行、助听、假肢及康复辅助器具等适老产品…"
  - 17 家："提供居家照护、专业护理及智慧养老等上门或机构化服务…"
  - 16 家："面向银发产业提供行业资讯、媒体内容与渠道服务…"
  - 16 家："搭建面向中老年用户的社交、文娱或兴趣社区平台…"
- 这些标签由假描述回灌，既错又不一致。

**P4 · 8 个大桶≥40 未真查**
- 居家护理 90 / 陪伴服务 75 / 助听器 63 / 助行器 58 / 养老机构 47 / 兴趣社群 43 / 可穿戴监测 41 / SaaS 40。规则要求≥40 必查，但实测 `validate_tags.py` 只报警 **>100**，**40–100 根本不提示**——漏洞。

**P5 · config ↔ 数据漂移**
- `抗衰` 在 config 的 食品营养 下列着，但 **0 家企业**使用（v15"抗衰老药物→抗衰+药品"的拆分只进了 config，没落库，相关企业仍只标"药品"）。
- `养老` 在 config 被挂在 **智能科技** 下（语义错误：Carewell 是零售/消费品公司，不是智能科技）。

**P6 · 「养老」标签本身该删**
- 仅 Carewell 1 家使用，且归属错。它违反"大伞词/横切不当标签"原则。建议删除，Carewell 回归 `电商+垂直电商`。

**P7 · 校验"全绿"≠"正确"**
- 9/10 项只查结构（重复、孤儿、数量），**完全不查语义对错**。前序 AI 可能把"校验通过"当成"标签对了"的证据——这是危险的误判。需补"单标签率/横切属性/大桶复查"等语义闸门。

**P8 · 可靠信号 business_tags 被闲置**
- 全库 1305 家**都有** `business_tags{customer,role,channel}`（如 `B2B/服务商/媒体`），这是比假 description 更可靠的分类依据，但当前打标几乎没用它。

## 五、详细规划（从哪入手，分 5 阶段）

> 铁律：Phase 0 只出方案不动数据；凡结构性决策（P3 怎么处理假描述、P6 删养老）先对齐再执行。

**Phase 0（当前）· 对齐**：交付本文 + 规则重构版 V1，小爽拍板。
**Phase 1 · 修地基（最关键）**：决定 164 家模板描述的处理方式——(A) 用真实信源重生成 description，或 (B) 分类时隔离 description、只用 name+business_tags。打标主信号切到 name+business_tags。
**Phase 2 · 补多标签**：重跑二次聚类，给每家企业补 2–3 个跨一级标签，单标签率压到 ≤40%。
**Phase 3 · 清大桶**：逐家复查 8 个≥40 桶，真拆/重分配（重点居家护理 90、陪伴服务 75、兴趣社群 43）；横切属性（SaaS/AI/智能硬件/可穿戴监测）降级为元数据。
**Phase 4 · 修漂移**：删「养老」、把"抗衰"要么落库要么移出 config；修 `_l2_l1.json` 让养老/抗衰归属正确。
**Phase 5 · 加固+同步**：补 validator 的 3 个语义闸门（≥40 报警、config↔数据零漂移、横切不占 L2）；重跑三生成器 + `gen_deliverables.py` 让文档与库同步；部署；commit main。

## 六、协作与沟通方式

- **模式**：本阶段是"先对齐再执行"。我先做研究+出方案，你审查拍板，再落地。不 silent 改数据。
- **大决策用文档不用选择题**：涉及结构（如 P3 选 A 还是 B、P6 删养老）我写详细方案文档给你慢慢看，不用四字选择题逼你。
- **透明交付**：每次改标签必附——一级列表+企业数、每级二级+企业数、**每个二级全部同类词（不省略）**、改动前后对照。不只报"校验通过"。
- **主动挖错**：不等你点名，同类潜在错误全量排查（本文 P1–P8 已一次列全）。
- **动你手标必标注**：凡改到你手动整理的内容，显式【动你标注】+理由。
- **节奏**：分析/写文档我可自主推进；任何写回 `all_enterprises.json` 的动作都设检查点，等你确认。
