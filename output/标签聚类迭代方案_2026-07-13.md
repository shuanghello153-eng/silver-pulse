# 标签聚类迭代优化方案（2026-07-13 讨论稿）

> 背景：v10 已完成「≥30 大标签全拆 + 聚类惊喜二次走查」，9/9 校验全绿（1324 家 / 61 二级 / 10 一级）。
> 本方案回应两个提议：(1) 建立标签迭代优化机制（自上而下，方案1）；(2) 直接对全库 1000+ 企业做自下而上聚类（方案2）。
> 目标：让标签体系能**自动越跑越准、可追踪、可衡量**，并在处理中**同步纠正企业信息错误**。

---

## 一、两种方案白话评估

### 方案1：自上而下迭代优化（基于现有标签）
- **做法**：把现有「二级标签下企业数 ≥30（或 ≥20）」的标签拎出来 → 聚类找自然子群 → 拆分该标签 / 把不属于的企业摘出去 → 重跑聚类 → 重复，直到「该标签下无错误」或「企业数降到 30 以下」。
- **优点**：站在你已经审过的体系上，不会把结构搞乱；直接打掉大伞词；停止条件具体。
- **缺点**：被现有标签词表「框死」——如果「鞋」「助听器细类」现在不是标签，它就永远不会冒出来；同时继承数据质量天花板（简介太泛的模板企业自动拆不动）。

### 方案2：自下而上从零聚类（从数据长标签）
- **做法**：先不看现有标签，用**最小粒度关键词/同类词**对全库 1324 家企业聚类；每个簇只用很紧的种子词（如「家庭护理/居家护理/居家照护/上门照护」算一簇），**颗粒度尽量细**；只有当某簇企业数 <5 且不是因为「漏了关键词」才放宽匹配词；每企业挂 1~3 个标签、按专属度排展示顺序；收敛后把涌现的簇映射到一级标签，再和现体系比对。
- **优点**：能**发现现有体系里没有的新类别**（鞋、助听器细分等）；「先细后放宽」正是正确的颗粒度纪律；能反过来检验现体系（哪些标签该加、哪些是虚的）。
- **缺点**：比较「颠覆」，可能和已审体系冲突；需要种子词库；「聚类不再改变」只在聚类是确定性的（正则匹配是，大模型不是）时才好定义；种子太窄会过度碎片化。

### 两者关系（关键结论）
**不是二选一，是同一件事的两遍：**
- 第 A 遍（方案2 自下而上）= 从数据里发现「真实的细颗粒类别空间」。
- 第 B 遍（方案1 自上而下）= 把涌现的簇并入现有 10 一级 / 61 二级体系，迭代到干净，按 <30 或「无错误」停止。
- 再加一遍**企业信息同步纠错**（描述与标签矛盾的企业，当场修正）。
→ 推荐**混合双通道**，而「两个智能体对照」正好对应这两遍：Agent A 跑自上而下，Agent B 跑自下而上，最后对账。

## 二、聚类引擎设计（参数 + 评估标准 + 停止条件）

### 输入
- `data/enterprise/all_enterprises.json`（name_cn/en + desc）。
- 同类词库 `data/enterprise/tag_synonyms.json`（用于种子词扩展）。

### 种子词典（每个簇的结构）
```
{
  "name": "居家护理",
  "l1_hint": "养老服务",
  "seed": ["居家","home care","家庭护理","居家照护","上门照护","家政","助浴","送餐","陪护","居家养老"],
  "relax": ["护理","照护"],            # 仅当 size<5 且非关键词缺失时启用
  "min_size": 5,
  "exclusive_with": ["养老机构","养老社区","专业护理"]   # 互斥裁剪
}
```
**颗粒度铁律（按你的要求）**：seed 只放最相关的词；不要把「社区 / 机构养老 / 专业护理」塞进居家养老；relax 词**只在簇 <5 且确认不是漏词时才加**。

### 迭代算法
```
round = 0; changed = True
while changed and round < MAX_ROUNDS(=8):
    round += 1
    对每家企业 e:
        matches = [c for c in clusters if 命中(e, c.seed)]          # 先只用紧种子
        if not matches and round>1:
            matches = [c for c in clusters if 命中(e, c.seed + c.relax)]  # 再放宽
        selected = 互斥裁剪(matches, e)        # 同时命中互斥簇时，保留更具体的
        e.tags = selected[:3]                  # 1~3 个，按专属度排序（具体的在前）
    changed = (本轮分配 != 上轮分配)
    记录本轮指标到日志
# 收敛 = changed == False（聚类不再改变）
```
命中规则：对 `(name + ' ' + desc).lower()` 做大小写不敏感子串/正则匹配；同类词展开后一并匹配。

### 每轮评估指标（可衡量）
| 指标 | 定义 | 目标 |
|---|---|---|
| 凝聚度 cohesion | 簇内含 ≥1 个 seed 词的成员占比 | ≥ 0.8 |
| 互斥污染 contamination | 同时命中互斥簇的企业数 | = 0 |
| 残差 residual | 未命中任何簇的企业数占比 | < 5% |
| 标签数分布 | 每企业 1~3 个 | 中位数目标 2 |
| 大伞词规模 | 原 ≥30 标签的企业数 | 逐轮下降 |

### 停止条件
- **方案1（单标签视角）**：该二级标签企业数 < 阈值（30 或 20） **或** （cohesion≥0.8 且 contamination=0 且 residual<5%）。
- **方案2（全库视角）**：连续两轮分配不变（收敛） **或** round==MAX_ROUNDS。

### 可追踪
每轮追加日志到 `output/_cluster_iter_log.txt`：`轮次 / 簇名 / 规模 / 本轮新增关键词 / 四项指标`。全程可回放、可量化。

## 三、双智能体协同设计

| | Agent A（自上而下·方案1） | Agent B（自下而上·方案2） |
|---|---|---|
| 输入 | 仅现有 ≥30 二级标签 + 其成员 | 全库 1324 家 + 独立种子词库 |
| 种子来源 | 现有 `tag_synonyms.json` | 我提供的独立细颗粒词库（与 A 不共享，保证独立） |
| 输出 | 精炼后的标签体系 + 误标清单 | 涌现的细颗粒类别 + 误标清单 |
| 纠错 | 同步修正描述/标签矛盾的企业 | 同步修正描述/标签矛盾的企业 |

**对账（由我执行）**：
- **一致集**（两方标签相同）→ 高置信，直接采纳。
- **分歧集**（不同）→ 列双方理由，交人工/大模型裁决。
- **仅 B 有**（涌现无对应）→ 候选新二级标签；**仅 A 有**→ 可能冗余/误标。

**可行性提醒**：本会话早些时候子智能体通道曾报错（`Cannot read properties of undefined (reading 'history')`）。执行前我会先探活；若仍不可用，则改为**直接用脚本跑两遍独立聚类**（同样产出两份独立结果供对照），不阻塞进度。

## 四、企业信息同步纠错规则
每轮扫描「描述与标签明显矛盾」的企业（如描述为「时尚网红」却挂 智慧养老；描述为「机器人」却挂 居家护理），列入 `@纠错清单`，**当场同步修正** desc/name 错误并重指派标签。与 v10 已做的「时尚奶奶团 / 腾讯」修正一脉相承，避免后续重复出错。

---

## 五、当前约束与风险（必须说清）
1. **数据质量天花板**：大量企业简介是模板占位（「运营养老社区或康养项目」），纯关键词聚类拆不动，真正收敛需要补全简介（大模型增强，目前**无 API/key**）。现实交付 = 在现有数据上跑出最优涌现体系 + 把残差模糊企业**标注待补全**，留待 LLM 增强轮。
2. **子智能体通道**：见第三节提醒。
3. **「无错误」需操作化定义**：用第二节的 cohesion/contamination/residual 三项量化，而非拍脑袋。
